# PRD: AI エージェントの導入

リポジトリの所有者が、どのマシンでも手作業の設定なしに、同じ振る舞いのエージェントを使えるようにするための要求と受入条件を定める。

- 読者: 開発者
- 段階: 5. デリバリー（要求と受入条件を確定し、実装済み）

この PRD の用語は次の意味で使う。

- エージェント: 指示を受けてコードを書き換える AI のプログラムのうち、端末の中で動かすもの。
- 文脈: エージェントが一度に扱える指示と履歴のまとまり。
- 作業手順: 特定の作業のときにエージェントが呼び出す、決まった手順の定義。
- 「すべて」「最小限」: PRD 0001「開発環境の導入」で定める導入範囲。
- Nix のない環境: ブラウザとスマホから使う Claude Code のように、このリポジトリの導入操作を行えない環境。

## 課題

### 問題と根拠

マシンが変わるたび、エージェントを使える状態にするまで手作業の設定が要る。

設定を持ち込むだけでは足りない。
既定のままでは操作のたびに確認待ちが挟まって作業が止まり、長い作業では扱える文脈が尽きて途切れる。
作業が終わっても入力待ちになっても、画面を見ていなければ気付けない。

指示や作業手順はマシンごと、作業ごとにばらつき、成果物の質が揃わない。
エージェントはコードの意味や最新の外部情報を参照できず、推測で書く。

Nix のない環境では、導入操作で配置した作業手順を読めない。
このリポジトリをブラウザやスマホから開いても、自作の作業手順を呼び出せない。

### 対象となる利用者

リポジトリの所有者本人だけを対象とする。

### 提供する価値

所有者は、新しいマシンでも手作業の設定なしに、同じ振る舞いのエージェントをすぐ使える。
設定を変えれば、その変更は全てのマシンへ同じ形で行き渡る。

確認待ちで作業が止まらず、あらかじめ定めた破壊的な操作は拒まれる。
長い作業でも文脈が尽きずに続き、画面を見ていなくても終了と入力待ちに気付ける。

どのマシン、どの作業でも同じ指示と作業手順が使えるため、成果物の質が揃う。
このリポジトリでは、Nix のない環境でも同じ作業手順を呼び出せる。
エージェントはコードの意味と最新の外部情報を参照して書く。

「最小限」を入れれば、壊れたマシンでもエージェントが使える。
復旧作業そのものをエージェントに任せられる。
コードの意味を引くことと、ブラウザを操作することは、「すべて」を導入した場合にだけできる。

### 対象外

- 作業手順の配布先として、他の種類のエージェントを有効にすること。取り込む仕組みは持つが、有効にする配布先は増やさない。
- 「最小限」でブラウザを操作すること。
- 「最小限」でコードの意味を引くこと。
- 圧縮の記録を読むこと、集計すること。
- 利用量に上限を設けて止めること。
- エージェント本体を自動で更新すること。
- このリポジトリ以外のリポジトリで、Nix のない環境に作業手順を自動で配ること。

### 制約とトレードオフ

所有者は、次のことを受け入れる。

- 確認待ちで作業を止めない代わりに、要求2で拒む操作に当てはまらない破壊的な操作は止まらない。
- 扱える文脈量を最大に保つ仕組みは、エージェント本体側の変更で効かなくなることがある。
- 本体を自動更新しない代わりに、新しい版は、所有者が版を上げるまで入らない。
- 外部の提供元から取り込む作業手順は、取り込み直すまで上流の更新が届かない。
- 本体を導入できるのは、x86_64 の Linux と Apple シリコンの macOS に限られる。
- 通信を中継する仕組みが止まると、エージェントは通信できない。
- 通知と状態表示は、リポジトリを決まった場所に置くことを前提とする。リポジトリを移動または削除すると、これらは動かなくなる。
- 通知は WSL と macOS だけで出る。それ以外の Linux では出ない。
- Nix のない環境では、作業手順の導入が終わるまでセッションが始まらない。
- Nix のない環境で取り込む外部の作業手順は版を固定しない。セッションを始めるたびに上流の最新が入る。

### 成功条件

新規のマシンまたは復旧したマシンに導入したあと、手作業の設定をせずに、要求がすべて満たされた状態でエージェントを使える。
「最小限」を入れたマシンでも、要求10 と要求12 を除いて同じく使える。
Nix のない環境では、このリポジトリを開いたときに要求17 を満たす。
数値目標は設けない。

### 計測と学習の計画

新規のマシンへの導入と、壊れたマシンの復旧のたびに、成功条件を満たしたかを確かめる。
手作業の設定や不具合が生じた場合は記録し、要求と対象外を見直す材料にする。

## 解決策

### 要求と受入条件

各要求と、その要求を受け入れる条件は次のとおり。

| # | 要求 | 受入条件 |
|---|---|---|
| 1 | 確認を求められずに実行する | 明示的に許可した操作以外でも、実行前の確認が挟まらない |
| 2 | 定めた破壊的な操作は常に拒む | 下記の操作は、所有者が承認しても実行されない |
| 3 | 画面を見ていなくても、終了と入力待ちに気付ける | 作業完了時と入力待ち時に、それぞれ OS の通知が出る |
| 4 | 作業中の状態が常に見える | 下記の項目が常に表示される |
| 5 | 長い作業でも扱える文脈量が減らない | 扱える文脈量が最大のまま表示され、長い作業でも途切れない |
| 6 | 文脈が圧縮されたとき、記録が残る | 圧縮が起きた時刻と作業場所が記録に残る |
| 7 | 全プロジェクト共通の指示が最初から効く | 何も指示しない状態で、下記の作法が指示どおりになる |
| 8 | 外部の提供元から作業手順を取り込む | 取り込んだ作業手順が一覧に現れ、呼び出せる |
| 9 | 自作の作業手順を呼び出せる | 下記の作業手順が一覧に現れ、呼び出せる |
| 10 | コードの意味を引ける | 「すべて」で定義や参照を引け、「最小限」では引けない |
| 11 | 外部の情報を引ける | 下記の情報を引ける |
| 12 | ブラウザを操作できる | 「すべて」で操作でき、「最小限」では使えない |
| 13 | 下位のエージェントを同一プロセスで走らせる | 任せた作業が、別のプロセスを起動せずに完了する |
| 14 | 使うモデルと思考の強度が決まっている | 起動時に、定めたモデルと思考の強度が選ばれる |
| 15 | エージェント本体を自動更新しない | 起動時に更新が始まらない |
| 16 | 生成物に共著者の記載を入れない | 生成したコミットに共著者の記載が入らない |
| 17 | Nix のない環境でも、このリポジトリで作業手順を呼び出せる | 下記の作業手順が、手作業の設定なしに一覧に現れ、呼び出せる |

要求10 と要求12 以外は、「すべて」と「最小限」のどちらの導入範囲でも満たす。
要求17 は、導入範囲によらず、Nix のない環境で満たす。

要求2で拒む操作は次のとおり。

- ファイルやディレクトリの消去
- 履歴の強制上書き
- 作業中の変更の破棄
- ディスクへの直接書き込み
- 権限の全開放

要求3の通知は、Windows 側と macOS の双方で出る。

要求4で表示する項目は、作業場所、ブランチ、使っているモデル、5時間と7日それぞれの利用量の割合である。

要求7の指示は、応答の作法、変更の進め方、検証の作法を定める。

要求9の作業手順は次の4種である。

- 変更を送り出す
- 設計と要求を文書に残す
- 依存を最新に保つ
- 文章を整える

要求11の情報は、ライブラリの文書、リポジトリの解説、インフラ定義の3種である。

要求17の作業手順は、要求9の作業手順のうち Nix に依存しないものと、それらが呼ぶ外部の作業手順である。

### 成功条件の測定方法

新規のマシンまたは復旧したマシンに導入したとき、所有者が受入条件を手作業で一つずつ確かめる。
あわせて、導入のほかに手作業の設定が要ったかを確かめる。
Nix のない環境では、このリポジトリで新しいセッションを始め、要求17 の受入条件を確かめる。
計測の仕組みは設けない。

### 展開計画

所有者のマシンだけに提供する。
段階的な公開はしない。
変更は、各マシンで導入操作をやり直した時点で、そのマシンに反映される。
Nix のない環境では、既定のブランチへ取り込んだあとに始めたセッションから反映される。
