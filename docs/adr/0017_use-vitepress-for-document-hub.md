# ADR: ドキュメントハブを VitePress で生成する

ドキュメントハブをどの方法で生成するかの決定を記録する。
サイトの生成には VitePress を使い、`docs/` の Markdown をそのまま読み込む。

- 読者: 開発者
- 状態: 採用
- 決定日: 2026-10-06

用語は PRD 0010 と同じ意味で使う。
ドキュメントハブ（以下、ハブ）は、`docs/` の Markdown を Web 上で閲覧できるようにするサイトを指す。
文書参照は、「ADR 0007」のように文書の種類と番号で別の文書を示す表記を指す。

## 背景

PRD 0010 では、`docs/` の文書について次の問題を挙げた。

- 目的の文書を探しにくい。
- 関連する文書をたどれない。
- 文書を一覧で把握できない。
- チームや協力者に共有しにくい。

これらを解決するため、PRD 0010 では案A「Web 上の専用サイト」を採った。
サイトをどの方法で生成するかは、PRD 0010 では決めていない。

## 制約

PRD 0010 の制約から、選べる案は次の条件を満たす必要がある。

- 正本は `docs/` の Markdown のままにし、ハブは表示だけを担う。
- 既存の文書と、文書を作るスキルの書き方を変えない。文書にはフロントマターがなく、冒頭の H1 と箇条書きにタイトルとメタ情報を書いている。
- 所有者一人で保守でき、運用費がかからない。

あわせて、PRD 0010 の機能要求1〜9を満たせる必要がある。
機能要求には、次のものが含まれる。

- 日本語のキーワードによる全文検索（機能要求2）
- 文書参照のリンク化（機能要求3）
- Mermaid の図の表示（機能要求6）
- ダークモードと、その手動での切り替え（機能要求7）
- 幅375px の画面での表示（機能要求9）

## 決定

ハブの生成には VitePress を使う。
VitePress の `srcDir` に `docs/` を指定し、`docs/` の Markdown を直接読み込む。

## 決定理由

- `docs/` を `srcDir` に指定すれば、フロントマターのない既存の文書を書き換えずに表示できる。書き方を変えないという制約を守れる。
- ダークモードの切り替えとスマートフォン向けの表示を標準で備える。機能要求7・9を設定だけで満たせるため、一人で保守できる範囲に収まる。
- Markdown の変換に markdown-it のプラグインを足せる。そのため、文書参照のリンク化（機能要求3）と Mermaid（機能要求6）を組み込める。
- 生成物は静的なファイルなので、運用費のかからない公開先に置ける。

## 代替案

次の案は、それぞれの理由で採らない。

- Astro Starlight: 各文書のフロントマターに `title` が必須である。既存の文書を変えずに読むには、独自のローダーを作って保守する必要がある。
- MkDocs Material: Python のツールチェーンが増える。リポジトリではすでに Node.js のツールチェーンを使っており、それとは別の言語のツールチェーンも保守することになる。
- remark や unified などで自作する案: 検索、ダークモード、スマートフォン向けの表示をすべて自分で作り、保守することになる。一人で保守できる範囲を超える。

## 結果

- Node.js のパッケージが1つ増え、その依存を更新し続ける。リポジトリにはすでに `apps/web` と `packages/dotfiles` に Node.js のパッケージがある。
- VitePress のサイドバーは設定ファイルに並べた項目から作られるため、文書を追加しただけでは項目が増えない。業務要求1を満たすため、`docs/` のファイル一覧からサイドバーを作る処理を自作し、保守する。
- 一覧のメタ情報（機能要求4）と文書参照のリンク化（機能要求3）は、VitePress の標準機能にない。本文の箇条書きと文書参照を読み取る処理を自作し、保守する。
- VitePress の標準の検索は日本語を分かち書きしない。そのため、標準のままでは日本語の全文検索（機能要求2）を満たせない。検索の方式は ADR 0018 で決める。
- URL はファイル名から決まるため、ファイル名を変えると URL も変わる。この点は PRD 0010 で受け入れ済みである。
