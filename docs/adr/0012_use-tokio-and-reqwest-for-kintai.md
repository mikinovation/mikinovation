# ADR: kintai は非同期で構成し、tokio と reqwest を使う

`kintai` を非同期で構成し、ランタイムに tokio を、HTTP クライアントに reqwest を使うという決定を記録する。

- 読者: 開発者
- 状態: 採用
- 決定日: 2026-10-03

`kintai` は、ADR 0007 で Rust で書くと決めた CLI を指す。
集計、検出、freee 連携は、設計書「勤怠表と請求書の作成」のコンポーネントを指す。

## 背景

ADR 0008 で、`kintai` が freee の API を呼ぶと決めた。
そのため、HTTP クライアントのクレートと、同期と非同期のどちらで構成するかを決める必要がある。
所有者は `kintai` 以外の機能も作る見込みが高く、それらの部品は Web API とも共有する予定がある。

## 制約

ADR 0007、ADR 0008 と所有者へのヒアリングから、選べる案は次の条件を満たす必要がある。

- freee 連携などの部品を、CLI と今後の Web API の両方から使える。
- 集計と検出は、ユニットテストで守れる。
- 導入範囲「すべて」で、所有者のマシンに Home Manager で導入できる。

## 決定

`kintai` は非同期で構成する。
ランタイムには tokio を、HTTP クライアントには reqwest を使い、TLS には rustls を使う。
認可コードの待ち受けには、tokio の TcpListener を使う。

外部と通信しない集計と検出は、同期の関数のままにする。

そのほかの依存には、次のクレートを使う。

- 引数の解析: clap
- 日付と時刻: chrono
- Org 形式の解析: regex
- TOML と JSON: serde、toml、serde_json
- 状態ファイルの置き換え: tempfile
- エラーの型: thiserror

## 決定理由

- Rust の主な Web フレームワークは tokio の上で動くため、freee 連携などの部品を、今後の Web API と同じ基盤で共有できる。
- 非同期は呼び出し元へ広がるため、共通の部品は最初から非同期で作るほうが、後から作り直すより手戻りが小さい。
- 集計と検出を同期の関数に保つため、CLI と Web API のどちらからも呼べ、テストも単純なままで済む。
- reqwest は Rust の HTTP クライアントとして広く使われ、今後ほかの外部の API を呼ぶときにも使える。

## 代替案

次の案は、それぞれの理由で採らない。

- 同期で構成し、ureq を使う案: 依存は少ない。しかし Web API と共有するには、呼び出しを包むか、非同期の版を別に持つ必要がある。
- reqwest の blocking 版を使う案: 内部で tokio を動かすため、依存は減らない。また、tokio の上で動く Web API から呼ぶと実行時エラーになる。

## 結果

- 同期で構成するより依存が増え、ビルドの時間とバイナリが大きくなる。
- 依存のクレートが多いぶん、nix 側のハッシュを更新する機会が増える。
- freee を差し替えるための trait は、async のメソッドを持つ。
- CLI の入口は、tokio のランタイムの上で起動する。
