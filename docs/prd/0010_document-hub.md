# PRD: ドキュメントハブ

`docs/` の文書を探しにくく、関連する文書をたどりにくいという課題について、問題と仮説を整理し、何を解決し何を解決しないかを定める。そのうえで、Web 上の専用サイトで解くための要求を定める。

- 読者: 開発者
- 段階: 5. デリバリー（要求と受入条件を確定した。実装は未着手）

この PRD の用語は次の意味で使う。

- ドキュメントハブ: `docs/` の Markdown を Web 上で閲覧できるようにするサイト。以下、ハブと呼ぶ。
- 文書参照: 本文中で別の文書を指す表記。「ADR 0007」「PRD 0004」のように、文書の種類と番号で書く。
- メタ情報: 各文書の冒頭の箇条書きに書く、読者、状態、段階などの情報。

## 課題

### 問題と根拠

所有者は、`docs/` の文書を読むときに次の問題を抱えている。

- 目的の文書を探しにくい。GitHub のファイル一覧と検索では、日本語の本文を横断して探しにくい。
- 関連する文書をたどれない。文書参照がリンクになっておらず、参照先を一つずつ開き直している。
- 文書を一覧で把握できない。どの ADR が採用されているか、どの PRD がどの段階かを一目で把握できない。

補助的な問題として、チームや協力者に、読み物として文書を共有しにくい。

リポジトリでは、次の事実を確かめた。

- `docs/` には26本の文書がある。内訳は ADR が16本、PRD が9本、設計書が1本である。
- 文書参照はすべて文字だけで書かれており、リンクになっていない。
- メタ情報は、各文書の冒頭の箇条書きにしかない。

探しにくさは所有者の経験に基づく。
問題の大きさを数値では検証していない。

### なぜ今か

PRD、ADR、設計書、テストケース、計画を作るスキルが揃い、文書はこれから継続的に増える。
`docs/test/` と `docs/plan/` もこれから追加され、文書の種類と文書参照が増える。
文書の件数が少ないうちにハブを作る方が、手間が少ない。

### 対象となる利用者

所有者と、チームや協力者を対象とする。

外部の閲覧者がハブを読むことは妨げないが、外部の閲覧者の問題は解かない。
ハブを公開するのは、隠す理由がないためである。

### 仮説

文書を Web 上で検索でき、文書参照をリンクでたどれるようになれば、次のことが起きる。

1. 関連する過去の決定（ADR や PRD）を見つける手間が減る。
2. 新しい文書を書くときに、既存の文書を参照する頻度が上がる。
3. チームや協力者に、URL ひとつで文書を共有できる。

### 提供する価値

所有者は、過去の ADR や PRD をすぐに見つけられる。
新しい文書を、既存の決定と食い違わないように書ける。

チームや協力者は、URL ひとつで最新の文書を読める。
各文書の状態（採用、段階など）を把握できる。

### 対象外

- `okf/` と `roam/` のノート。
- このリポジトリの外にある文書。ほかのリポジトリ、Notion、Google Docs などを含む。
- `docs/` 以外の Markdown。README、SKILL.md、AGENTS.md などを含む。
- 外部の閲覧者に向けた導入ページ、用語の説明、文章の品質向上。
- 認証とアクセス制御。
- 多言語化。
- Web 上での文書の編集。

### 制約とトレードオフ

ハブは次の制約を守る。

- 正本は Git 上の Markdown とし、ハブは表示だけを担う。
- リポジトリは公開されており、ハブも検索エンジンに載る形で公開する。そのため、機密情報を `docs/` に書かない運用を前提とする。非公開のデータは、別の非公開リポジトリに置く。
- 既存の文書と、文書を作るスキルの書き方を、ハブの都合で変えない。GitHub 上でも、今のまま読める状態を保つ。
- 所有者一人で保守できる範囲にとどめ、運用費をかけない。

所有者は、次のことを受け入れる。

- 認証を持たず、仕組みを簡素にする。その代わりに、誤って書いた内容がすぐに公開され、検索エンジンに載るおそれがある。
- 文書の書き方を変えずにスキルとの整合を保つ代わりに、ハブに表示できるメタ情報は、今の書き方から読み取れる範囲に限られる。
- 保守の負担を抑える代わりに、ハブの機能を絞る。どの機能を持たせるかは、段階4で定める。
- 問題の大きさを、数値で検証しないまま進める。検証は、段階6の振り返りで行う。
- チームや協力者が同じ問題を感じているかを、確かめないまま進める。公開後に URL を伝えるときに意見を聞き、段階6で反映する。

### 成功条件

ハブを提供できているかは、次の条件で判断する。

- `docs/` のすべての文書が、push の後に自動で公開されている。
- 本文中の文書参照が、すべてリンクになっている。
- 日本語のキーワードで全文を検索し、目的の文書を見つけられる。

ハブの成果は、次の条件で判断する。

- 新しく書いた文書で、既存の文書を参照する回数が増えている。
- チームや協力者と文書を共有するときに、ハブの URL が使われている。

### 計測と学習の計画

提供の条件は、公開後に次の方法で確かめる。

- `docs/` の文書数と、ハブに載っている文書数が一致するかを確かめる。
- リンクにできなかった文書参照が0件であることを確かめる。
- 代表的な日本語のキーワードを数件決めて検索し、目的の文書が見つかるかを手作業で確かめる。

成果の条件は、次の方法で確かめる。

- 公開前に既存の26本について、1本あたりの文書参照の数を数え、基準として記録する。公開後に書いた文書の同じ値と比べる。
- アクセス解析は入れない。ハブの URL を共有に使ったかは、振り返りのときに所有者が申告する。

公開から3か月後に、段階6として振り返り、結果を仮説1〜3と比べる。
仮説1は数値では測らず、使ってみた感想として記録する。

## 解決策

### 解決案とトレードオフ

次の3案を比べ、案Aを採った。

| 案 | 振る舞い | 利点 | 欠点 |
|---|---|---|---|
| A. Web 上の専用サイト | 検索、種類別のメニュー、一覧を備え、文書参照がリンクになったサイトで読む | 問題 a〜d をすべて解く | 保守するものが一つ増える |
| B. GitHub 上の索引ファイル | `docs/` に自動で作る一覧ページを、GitHub 上で開く | 新しいサイトが要らない | 探しにくさとたどりにくさ（a と b）が残る |
| C. 手元のアプリで閲覧 | Obsidian などのノートアプリで `docs/` を開く | 検索とリンクが強力 | URL で共有できず、d が残る。各自の導入が要る |

案Bは一覧の問題（c）しか解けず、案Cは共有の問題（d）を解けない。

所有者は、案Aについて次のことを受け入れる。

- 保守するものが一つ増える。この負担は、制約（一人で保守できる範囲にとどめ、機能を絞る）の中で引き受ける。
- ファイル名を変えると URL が変わり、それまでに共有したリンクは切れる。そのため、URL ひとつで共有できるという価値（問題 d）は一部弱まる。

### 要求と受入条件

業務要求と、各要求を受け入れる条件は次のとおり。

| # | 業務要求 | 受入条件 |
|---|---|---|
| 1 | 文書を `docs/` に書いて push するだけでハブに公開できる | ほかのファイルを変えなくても、新しい文書を追加して push するとハブに載る |
| 2 | 文書を作るスキルが書いたファイルを、手を加えないままハブで読める | スキルが書いたままの文書が表示され、一覧にメタ情報が出る |

業務要求1では、索引の更新や設定の追記など、ハブのための追加の作業を要らなくする。
業務要求2のスキルは、PRD、ADR、設計書、テストケース、計画を作るスキルである。

機能要求と、各要求が解く問題と受入条件は次のとおり。

| # | 要求 | 解く問題 | 受入条件 |
|---|---|---|---|
| 1 | 5種類の文書を、種類別のメニューから開ける | a | 文書がある種類がメニューに並び、各種類の全文書を開ける |
| 2 | 日本語のキーワードで全文を検索し、該当する文書を開ける | a | 既存の文書の本文にある日本語の語で検索すると、その文書が結果に出る |
| 3 | 本文中の文書参照がリンクになり、参照先へ移れる | b | 既存の文書の文書参照がすべてリンクになり、参照先を開ける |
| 4 | 種類ごとの一覧で、各文書の番号、タイトル、メタ情報が見られる | c | 一覧に番号とタイトルが出る。ADR は状態、PRD は段階が出る |
| 5 | 各文書に URL があり、本文を更新しても変わらない | d | 本文だけを変えて push した後も、その文書の URL が変わらない |
| 6 | Mermaid の図が図として表示される | 読みやすさ | Mermaid のコードブロックが図として表示される |
| 7 | ダークモードで読める | 読みやすさ | OS がダークモードならダークモードで表示され、手動でも切り替えられる |
| 8 | push の後、自動でハブに反映される | 業務要求1 | main ブランチへの push の後、10分以内にハブに反映される |
| 9 | スマートフォンでも崩れずに読める | 共有しやすさ | 幅375px の画面で、ページ全体を横にスクロールせずに本文を読める |

要求1の5種類は、PRD、ADR、設計書、テストケース、計画である。
テストケースと計画は、`docs/test/` と `docs/plan/` が追加された時点で載せる。
文書が0件の種類は、メニューに出さない。

要求3では、参照先が存在しない文書参照はリンクにせず、文字のまま表示する。
「ADR 0007 から ADR 0013」のような範囲の参照は、範囲内に存在する文書すべてへのリンクを並べて表示する。
どちらの場合も、文書の書き方は変えない。

要求4のメタ情報は、ADR の状態、PRD の段階などである。
メタ情報を読み取れない文書は、その欄を空欄にする。

要求5では、ファイル名を変えたときは URL も変わる。
古い URL は引き継がない。

要求7では、OS の設定に従って表示を切り替え、手動でも切り替えられるようにする。
手動で選んだ表示は、ページを移っても保たれる。

要求9では、広い表は表の中だけで横にスクロールできればよい。

各文書から GitHub 上の元のファイルを開く機能も検討したが、制約に従って機能を絞るため、要求に入れなかった。

### 成功条件の測定方法

「計測と学習の計画」を、次の方法で具体化する。

- 反映漏れ: 公開時と振り返りのときに、`docs/` の文書数とハブの一覧の文書数を比べる。
- 文書参照のリンク: 公開時に、リンクにならなかった文書参照が0件であることを確かめる。存在しない番号への参照は数えない。
- 検索: 公開時にキーワードを5語決めて記録し、それぞれで目的の文書が結果に出るかを確かめる。振り返りでも、同じ5語で確かめる。
- 参照の増加: 本文中の「PRD」「ADR」と4桁の番号の組を数える。公開前に、既存の26本の1本あたりの平均を基準として記録する。公開後3か月の間に書いた文書の平均と比べる。
- URL の利用: 振り返りのときに、所有者が申告する。

### 展開計画

- main ブランチの内容だけをハブに載せる。作業中のブランチは載せない。
- 段階的な公開はしない。検索エンジンも含めて、最初から全員に公開する。
- 公開前に、文書参照の数の基準を記録する。
- 公開後は、受入条件を確かめてから、チームや協力者に URL を伝える。そのときに、同じ問題を感じているかについて意見を聞く。

## 未解決の問い

現時点で、未解決の問いはない。

段階4までに残していた問いは、次のように決着させた。

- 問題の大きさの検証と、チームや協力者の意見の確認は、行わないまま進める。この判断は「制約とトレードオフ」に記した。
- 仮説1は、使ってみた感想だけで測る。
- 外部の閲覧者は、今回は対象となる利用者に含めない。段階6で見直す。
