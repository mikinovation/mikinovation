# PRD: ドキュメントハブ

`docs/` の文書を探しにくく、関連する文書をたどりにくいという課題について、問題と仮説を整理し、何を解決し何を解決しないかを定める。

- 読者: 開発者
- 段階: 3. 定義（課題の範囲、制約、成功条件を定めた。解決策は未着手）

この PRD の用語は次の意味で使う。

- ドキュメントハブ: `docs/` の Markdown を Web 上で閲覧できるようにするサイト。以下、ハブと呼ぶ。
- 文書参照: 本文中で別の文書を指す表記。「ADR 0007」「PRD 0004」のように、文書の種類と番号で書く。
- メタ情報: 各文書の冒頭の箇条書きに書く、読者、状態、段階などの情報。

## 課題

### 問題と根拠

所有者は、`docs/` の文書を読むときに次の問題を抱えている。

- 目的の文書を探しにくい。GitHub のファイル一覧と検索では、日本語の本文を横断して探しにくい。
- 関連する文書をたどれない。文書参照がリンクになっておらず、参照先を一つずつ開き直している。
- 文書を一覧で把握できない。どの ADR が採用されているか、どの PRD がどの段階かを一目で把握できない。

補助的な問題として、チームや協力者に、読み物として文書を共有しにくい。

リポジトリでは、次の事実を確かめた。

- `docs/` には26本の文書がある。内訳は ADR が16本、PRD が9本、設計書が1本である。
- 文書参照はすべて文字だけで書かれており、リンクになっていない。
- メタ情報は、各文書の冒頭の箇条書きにしかない。

探しにくさは所有者の経験に基づく。
問題の大きさを数値では検証していない。

### なぜ今か

PRD、ADR、設計書、テストケース、計画を作るスキルが揃い、文書はこれから継続的に増える。
`docs/test/` と `docs/plan/` もこれから追加され、文書の種類と文書参照が増える。
文書の件数が少ないうちに仕組みを作る方が、手間が少ない。

### 対象となる利用者

所有者と、チームや協力者を対象とする。

外部の閲覧者がハブを読むことは妨げないが、外部の閲覧者の問題は解かない。
ハブを公開するのは、隠す理由がないためである。

### 仮説

文書を Web 上で検索でき、文書参照をリンクでたどれるようになれば、次のことが起きる。

1. 関連する過去の決定（ADR や PRD）を見つける手間が減る。
2. 新しい文書を書くときに、既存の文書を参照する頻度が上がる。
3. チームや協力者に、URL ひとつで文書を共有できる。

### 提供する価値

所有者は、過去の ADR や PRD をすぐに見つけられる。
新しい文書を、既存の決定と食い違わないように書ける。

チームや協力者は、URL ひとつで最新の文書を読める。
各文書の状態（採用、段階など）を把握できる。

### 対象外

- `okf/` と `roam/` のノート。
- このリポジトリの外にある文書。ほかのリポジトリ、Notion、Google Docs などを含む。
- `docs/` 以外の Markdown。README、SKILL.md、AGENTS.md などを含む。
- 外部の閲覧者に向けた導入ページ、用語の説明、文章の品質向上。
- 認証とアクセス制御。
- 多言語化。
- Web 上での文書の編集。

### 制約とトレードオフ

ハブは次の制約を守る。

- 正本は Git 上の Markdown とし、ハブは表示だけを担う。
- リポジトリは公開されており、ハブも検索エンジンに載る形で公開する。そのため、機密情報を `docs/` に書かない運用を前提とする。非公開のデータは、別の非公開リポジトリに置く。
- 既存の文書と、文書を作るスキルの書き方を、ハブの都合で変えない。GitHub 上でも、今のまま読める状態を保つ。
- 所有者一人で保守できる範囲にとどめ、運用費をかけない。

所有者は、次のことを受け入れる。

- 認証を持たず、仕組みを簡素にする。その代わりに、誤って書いた内容がすぐに公開され、検索エンジンに載るおそれがある。
- 文書の書き方を変えずにスキルとの整合を保つ代わりに、ハブに表示できるメタ情報は、今の書き方から読み取れる範囲に限られる。
- 保守の負担を抑える代わりに、ハブの機能を絞る。どの機能を持たせるかは、段階4で定める。

### 成功条件

ハブを提供できているかは、次の条件で判断する。

- `docs/` のすべての文書が、push の後に自動で公開されている。
- 本文中の文書参照が、すべてリンクになっている。
- 日本語のキーワードで全文を検索し、目的の文書を見つけられる。

ハブの成果は、次の条件で判断する。

- 新しく書いた文書で、既存の文書を参照する回数が増えている。
- チームや協力者と文書を共有するときに、ハブの URL が使われている。

### 計測と学習の計画

提供の条件は、公開後に次の方法で確かめる。

- `docs/` の文書数と、ハブに載っている文書数が一致するかを確かめる。
- リンクにできなかった文書参照が0件であることを確かめる。
- 代表的な日本語のキーワードを数件決めて検索し、目的の文書が見つかるかを手作業で確かめる。

成果の条件は、次の方法で確かめる。

- 公開前に既存の26本について、1本あたりの文書参照の数を数え、基準として記録する。公開後に書いた文書の同じ値と比べる。
- アクセス解析は入れない。ハブの URL を共有に使ったかは、振り返りのときに所有者が申告する。

公開から3か月後に、段階6として振り返り、結果を仮説1〜3と比べる。
仮説1は数値では測らず、使ってみた感想として記録する。

## 未解決の問い

- 問題の大きさを、数値で検証していない。
- チームや協力者が同じ問題を感じているかを確かめていない。課題を定める前に、関係者の意見を集めていない。
- 仮説1を、使ってみた感想以外の方法で測れるか。
- 将来、外部の閲覧者を対象となる利用者に含めるか。
