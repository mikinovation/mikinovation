# PRD: 勤怠表と請求書の作成

所有者が、日々の打刻から月末の勤怠表 PDF と freee の請求書の下書きまでを、案件ごとの精算のルールに従って誤りなく短時間で作れるようにするための要求と受入条件を定める。

- 読者: 開発者
- 段階: 5. デリバリー（要求と受入条件を確定し、実装前）

この PRD の用語は次の意味で使う。

- 案件: 所有者が稼働する契約の単位。同時に稼働する案件は常に1つとする。
- 打刻: その日の稼働の開始と終了を、Org 形式のファイルに clock の記録として残すこと。
- 日ごとの見出し: 案件の見出しの下に、1日に1つ作る見出し。打刻、休憩の例外、備考をここに書く。
- 勤怠表: 対象月の日ごとの始業、終業、休憩、稼働と、月の精算を載せた PDF。先方に提出する。
- 精算幅: 月の稼働時間の下限と上限。下限を下回ると控除、上限を超えると超過として精算する。
- 稼働率: 月の途中で契約が始まる月や終わる月に、月額と精算幅に掛ける比率。先方が示す。
- 基本額: 精算する前の月の請求額。月額に稼働率を掛けた額で、日割り月以外は月額と同じ。
- 日割り月: 稼働率を使う、契約の開始月と終了月。
- 下書き: freee で作る、発行前の請求書。
- skill: Claude Code に月末の作業を頼むための作業手順。
- 「すべて」「最小限」: 開発環境の導入範囲。PRD「開発環境の導入」（`docs/prd/0001_environment-setup.md`）で定める。

## 課題

### 問題と根拠

所有者は、毎月の勤怠表をスプレッドシートに手で記入し、PDF にして請求書と一緒に先方へ提出している。
この作業に、毎月、月末に30分ほどかかる。
時刻の15分単位の丸め、精算幅との比較、超過額と控除額の計算を、手作業と目視で行っている。
これまでに、記入や計算の誤り、先方からの差し戻しが起きている。
精算幅、単価、丸め方、日割りといった精算のルールは、案件ごとに変わる。

2026年9月に新しい案件が始まり、日割りと精算の計算が発生した。
そのため、今取り組む。

### 対象となる利用者

所有者本人だけを対象とする。

### 仮説

日々の打刻を Org 形式の clock で記録し、月末に勤怠表と請求の内容を自動で生成すれば、次のことが起きると見込む。

- 月末の作業が、30分から5分以内に縮む。
- 計算の誤りによる差し戻しがなくなる。

### 提供する価値

所有者は、月末に Claude へ一言頼むだけで、先方に出せる勤怠表 PDF と freee の請求書の下書きを揃えられる。
丸め、精算、日割りの計算は、案件ごとの設定に従って毎回同じ結果になるため、所有者が確かめ直す必要がない。
打刻漏れや、日割り月の設定の入力漏れは、勤怠表と下書きを作る前に検出される。

### 対象外

- 1日のうちに複数の案件で稼働すること。
- 請求書の発行と、先方への送付を自動で行うこと。
- 請求書の PDF を freee を使わずに作ること。
- 先方が指定する勤怠表の様式を再現すること。
- 祝日を判定すること。
- 日割り月の稼働率を自動で計算すること。
- チケットごとの作業時間や作業内容を記録すること。
- 所有者以外が使うこと。

### 制約とトレードオフ

所有者は、次のことを受け入れる。

- 休憩は案件ごとの既定値を使い、例外の日だけ明示する。その代わり、実際に取った休憩の時間は記録しない。
- 始業は切り上げ、終業は切り捨てて丸める。その代わり、15分未満の稼働は請求に含まれない。
- 日割り月の稼働率と精算幅は、先方が示した値を手で入力する。その代わり、入力の手間と入力漏れの危険を引き受ける。入力漏れは検出で補う。
- 超過額と控除額は、10円未満を切り捨てる。
- freee の API を使うために、認証の準備と、その情報の管理を引き受ける。
- 請求書の発行と送付は、所有者が freee の画面で行う。
- 勤怠の記録と案件の設定は非公開のリポジトリで管理するため、このリポジトリだけでは使えない。

### 成功条件

- 月末の作業が5分以内に終わる。作業は、勤怠表 PDF の生成から freee の下書きの作成までとする。
- 計算の誤りを理由に、先方から差し戻されない。
- 打刻漏れがある状態や、日割り月の設定が入力されていない状態では、勤怠表 PDF も下書きも作られない。

### 計測と学習の計画

最初の月である2026年9月分は、今の手作業のスプレッドシートと並行して作り、時間、精算額、請求額が一致するかを突き合わせる。
2026年9月分から11月分までの3か月は、月末の作業時間と差し戻しの有無を、所有者がメモに残す。
その結果を仮説と比べ、運用の段階で結果と学びに記す。
これ以外の計測の仕組みは設けない。

## 解決策

### 解決案とトレードオフ

#### 打刻の記録の仕方

次の3案を比べ、案1を採った。

| 案 | 利点 | 欠点 |
|---|---|---|
| 1. 日ごとの見出しに、朝に開始し、夜に終了する打刻をする | 始業、終業、休憩をそのまま取り出せ、休憩の既定値のルールを表せる | 作業の内訳は残らない |
| 2. チケットに打刻し、案件ごとに集計する | 作業の内訳も残る | 休憩が打刻の空白になり、休憩の既定値のルールとずれる |
| 3. 後から時刻を手で入力する | 打刻を忘れても困らない | 今の手作業と変わらない |

#### 操作の窓口と計算の担い手

次の3案を比べ、案1を採った。

| 案 | 利点 | 欠点 |
|---|---|---|
| 1. skill が窓口になり、計算は CLI が行う | 計算は毎回同じ結果になる。例外への対応は Claude が案内する | CLI と skill の両方を保守する |
| 2. skill だけで完結させる | 作るものが少ない | 金額の計算結果がぶれる余地が残る |
| 3. CLI だけで完結させる | Claude がなくても動く | 打刻漏れの修正などの例外への対応を、毎回所有者が判断する |

#### freee との連携

次の3案を比べ、案1を採った。

| 案 | 利点 | 欠点 |
|---|---|---|
| 1. 請求書の下書きを作る | 発行の前に所有者が確認できる | 発行と送付は手作業で残る |
| 2. 請求書を発行する | 手作業がさらに減る | 誤った金額でも発行される |
| 3. 先方への送付まで行う | すべて自動になる | 誤りに気付く機会がなくなる |

#### 日割り月の稼働率

次の2案を比べ、案1を採った。

| 案 | 利点 | 欠点 |
|---|---|---|
| 1. 先方が示した値を手で入力する | 先方の数字と必ず一致する | 入力の手間と、入力漏れの危険がある |
| 2. 営業日から自動で計算する | 入力が要らない | 先方の計算方法とずれる危険がある。祝日のデータが要る |

### 要求と受入条件

各要求と、その要求を受け入れる条件は次のとおり。
受入条件の金額と時間は、表の下に示す例の契約条件で計算した値である。

| # | 要求 | 受入条件 |
|---|---|---|
| 1 | その日の見出しに打刻できる | 1回の操作で、案件の見出しの下に当日の見出しができ、打刻が始まる。当日の見出しがすでにあれば、その見出しを使う |
| 2 | 休憩の例外を日ごとに指定できる | 日ごとの見出しに休憩の時間を書いた日は、その時間が休憩になる。書いていない日は、案件の既定値が休憩になる |
| 3 | 備考を日ごとに書ける | 日ごとの見出しに書いた備考が、勤怠表の備考の欄に載る |
| 4 | 案件ごとに精算のルールを設定できる | 契約期間、月額、精算幅、超過単価、控除単価、丸めの単位と向き、休憩の既定値、締め日、請求の項目を案件ごとに設定でき、設定を変えると計算結果が変わる |
| 5 | 日割り月の稼働率と精算幅を上書きできる | 例の契約条件の日割り月に稼働率0.5と精算幅70–90hを指定すると、基本額が ¥400,000、精算幅が 70–90h になる |
| 6 | 時刻が設定どおりに丸められる | 丸めの単位を15分、始業を切り上げ、終業を切り捨てに設定すると、始業9:58は10:00に、終業19:07は19:00になる |
| 7 | 精算額が設定どおりに計算される | 要求5の日割り月で、稼働91hなら ¥400,000 ＋ 1h × ¥4,440 ＝ ¥404,440 になる。稼働69.75hなら、控除額 0.25h × ¥5,710 ＝ ¥1,427.5 を切り捨てて ¥1,420 とし、¥398,580 になる。精算幅の範囲内なら ¥400,000 になる |
| 8 | 打刻漏れを検出できる | 終了のない打刻や、日をまたぐ打刻があると、その日付を示して止まる。勤怠表も下書きも作られない |
| 9 | 日割りの設定漏れを検出できる | 契約の開始月または終了月に稼働率の上書きがないと、その月を示して止まる。勤怠表も下書きも作られない |
| 10 | 勤怠表 PDF を生成できる | 対象月の全日が行になる。列は日付、曜日、始業、終業、休憩、稼働、備考で、稼働のない日は時刻の欄が空になる。ヘッダーに対象月、氏名、案件名、先方名が載る。表の下に合計時間、精算幅、超過または控除の時間、精算額が載る |
| 11 | freee に請求書の下書きを作れる | 対象月の精算額にもとづく品目、数量、単価、税率、支払期日で、freee に下書きができる。請求書は発行されない |
| 12 | 勤怠表と請求書を一緒に提出できる | 勤怠表 PDF が、freee から請求書と一緒に送れる形で用意される |
| 13 | 一言で月末の作業を頼める | 「9月の勤怠と請求書を作って」と頼むと、skill が検出、勤怠表の生成、下書きの作成を順に行い、PDF の場所と下書きを報告する。検出で止まった場合は、直すべき箇所を案内する |
| 14 | 同じ月の下書きを二重に作らない | 対象月の下書きがすでに freee にあると、そのことを知らせて止まる。新しい下書きは作られない |

受入条件の例に使う契約条件は次のとおり。
実際の案件の値ではない。

| 項目 | 値 |
|---|---|
| 月額 | ¥800,000（税別） |
| 精算幅 | 140–180h |
| 超過単価 | ¥4,440（¥800,000 ÷ 180h の10円未満を切り捨て） |
| 控除単価 | ¥5,710（¥800,000 ÷ 140h の10円未満を切り捨て） |
| 丸め | 15分単位。始業は切り上げ、終業は切り捨て |
| 超過額と控除額の丸め | 10円未満を切り捨て |

### 成功条件の測定方法

- 作業時間: 2026年9月分から11月分まで、skill に頼んでから下書きができるまでの時間を所有者がメモに残し、5分以内かで判断する。
- 差し戻し: 同じ3か月に、計算の誤りによる差し戻しがあったかを記録する。
- 入力漏れ: 要求8と要求9の受入条件を満たすことで確かめる。

計測の仕組みは設けない。

### 展開計画

所有者のマシンだけに提供する。
開発環境を「すべて」の範囲で導入すると使える。「最小限」には含まれない。
使う前に、所有者が次のものを用意する。

- 案件の設定と勤怠の記録を置く、非公開のリポジトリ
- freee の API の認証

2026年9月分は手作業と並行して作り、結果が一致したら、10月分から手作業をやめる。
段階的な公開はしない。
