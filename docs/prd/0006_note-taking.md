# PRD: ノートとタスクの管理

所有者が、エディターの中でナレッジノートと開発チケットを管理し、ノートを後から探しやすく、自分が手を動かすべきチケットを一目で判別できるようにするための要求と受入条件を定める。

- 読者: 開発者
- 段階: 5. デリバリー（要求と受入条件を確定し、実装済み）

この PRD の用語は次の意味で使う。

- ナレッジノート: 所有者が知識や判断を書き残す、1件ごとのノート。ノート同士をリンクでつなげる。
- メタデータ: ノートの種類、説明、タグ、作成日時の4つの欄。
- チケット: 開発作業の単位。作業状態を持つ見出しとして書く。
- 手番: そのチケットを次に進めるのが、所有者か他者か。
- アジェンダ: 開いているチケットを集めた一覧。
- 受信箱: 分類前のメモやタスクをいったん置くファイル。
- 「すべて」「最小限」: 開発環境の導入範囲。PRD「開発環境の導入」（`docs/prd/0001_environment-setup.md`）で定める。

## 課題

### 問題と根拠

ナレッジノートに種類やタグなどのメタデータがないと、ノートが増えるにつれて、人と AI エージェントのどちらからもノートを探しにくくなる。
メタデータを付けるかどうかを所有者の注意に任せると、付け忘れたノートが残る。

開発チケットは、未着手から完了まで11の状態を経る。
状態を一つずつ順に切り替える方法では、目的の状態に変えるまでの操作が多すぎて使えない。
また、状態を段階ごとの色で表すと、色の種類が多すぎて見分けられない。
その結果、自分が手を動かすべきチケットを一目で判別できない。

### 対象となる利用者

リポジトリの所有者本人だけを対象とする。
AI エージェントは、ナレッジノートを読む側としてだけ想定する。

### 提供する価値

所有者は、ノートを作った時点で、分類に使うメタデータの欄が揃った状態から書き始められる。
分類し忘れたノートを、後から一覧で拾える。
開いているチケットのうち、自分の手番のものがすぐにわかる。

### 対象外

- ノート全体の関係をグラフで表示すること。
- ノートのタグを補完すること。
- Emacs でノートとタスクを扱うこと。
- Claude のセッションログをアジェンダに出すこと。

### 制約とトレードオフ

所有者は、次のことを受け入れる。

- タグに複数の値を持たせるために、メタデータをノートのプロパティではなく、ノートの本文に YAML で埋め込む。
- 完了状態を一つにまとめる。その代わり、受け入れ済み、日常の雑務の完了、中止を状態で区別しない。
- 状態の色を手番で分ける。その代わり、色からは個々の段階がわからない。
- Claude のセッションログをアジェンダから外す。その代わり、セッションログに残った未完了の見出しは、アジェンダでは見えない。

### 成功条件

- 新しいナレッジノートが、すべて作成時点でメタデータの欄を持つ。
- タグのないナレッジノートの一覧を空にできる。
- 開いているチケットを、手番がわかる形で一覧できる。

数値目標は設けない。

### 計測と学習の計画

計測の仕組みは設けない。
所有者が、タグのないノートの一覧とアジェンダを普段の利用の中で確かめる。
使いにくさや不足に気づいた場合は、要求と対象外を見直す材料にする。

## 解決策

### 解決案とトレードオフ

#### メタデータの持ち方

次の2案を比べ、案2を採った。

| 案 | 利点 | 欠点 |
|---|---|---|
| 1. ノートのプロパティとして持つ | ノートの標準的な書き方に沿う | 1つの欄に複数の値を持てない |
| 2. ノートの本文に YAML で埋め込む | タグに複数の値を持てる | 記録なし |

#### ノート同士の関係の見方

次の3案を比べ、ノートとリンクがまだ少ないため、当面は案1で運用すると決めた。
ノートが増えて全体を俯瞰したくなった時点で、案2を再検討する。

| 案 | 利点 | 欠点 |
|---|---|---|
| 1. 標準のバックリンク表示で済ませる | 追加の作業がなく、エディター内で完結する | 1件のノートの前後しかたどれず、全体の構造は見えない |
| 2. ノートからグラフを生成する仕組みを自作する | ノート全体の構造を俯瞰できる | 作成と保守の手間がかかる |
| 3. 関係を表示する Web 画面を自作する | 自由に作り込める | 手間が最も大きい |

#### チケットの状態の変え方

キーを押すたびに状態を順に切り替える方式ではなく、絞り込める一覧から状態を選ぶ方式を採った。
11の状態を一つずつ送る方式は、操作が多すぎて使えないためである。
状態ごとの短縮キーも、覚える負担に見合わないため設けない。

### 要求と受入条件

各要求と、その要求を受け入れる条件は次のとおり。

| # | 要求 | 受入条件 |
|---|---|---|
| 1 | 新しいノートを作ると、メタデータの欄が揃う | 新規作成したノートに種類、説明、タグ、作成日時の欄があり、作成日時が自動で入る |
| 2 | ノートの種類を補完できる | 種類の欄で、6つの種類と各種類の説明が候補に出る。種類の欄以外では出ない |
| 3 | タグのないノートを一覧から開ける | タグの欄がない、またはタグが空のノートだけが一覧に出て、選ぶとそのノートが開く。該当するノートがない場合は、その旨が通知される |
| 4 | ノート同士をリンクし、リンク元を確かめられる | あるノートから、そのノートにリンクしているノートを表示できる |
| 5 | チケットの状態を一覧から選んで設定できる | カーソルに最も近い見出しの状態を、11の状態または「なし」に変えられる。見出しの本文は変わらない |
| 6 | 手番を色で判別できる | 未着手、所有者の手番、他者の手番が、それぞれ別の色の帯で表示される。完了は目立たない色で表示される |
| 7 | 開いているチケットを状態の順に一覧できる | アジェンダに、チケットが状態の順で並ぶ。Claude のセッションログは含まれない |
| 8 | 受信箱をすぐ開ける | 1回の操作で受信箱が開く |
| 9 | 見出しに ID を付けられる | 見出しに ID がなければ付与される。すでにあれば、その ID が保たれる |
| 10 | 選択範囲を Markdown としてコピーできる | 選択範囲が Markdown に変換されてクリップボードに入る。変換できない場合は、エラーが通知される |

要求2の6つの種類は次のとおり。

| 種類 | 説明 |
|---|---|
| note | 日常のメモ、永続ノート |
| reference | 外部資料の参照 |
| project | プロジェクト単位のノート |
| person | 人物に関するノート |
| meeting | 会議、商談の議事録 |
| decision | 意思決定、トレードオフの記録 |

要求5の11の状態と、要求6の色分けは次のとおり。

| 順 | 状態 | 手番による色分け |
|---|---|---|
| 1 | 未着手 | 未着手 |
| 2 | ISSUE 作成 | 所有者 |
| 3 | 設計 | 所有者 |
| 4 | テストケース作成 | 所有者 |
| 5 | 実装 | 所有者 |
| 6 | セルフレビュー | 所有者 |
| 7 | レビュー | 他者 |
| 8 | QA 中 | 他者 |
| 9 | QA 完了 | 他者 |
| 10 | 受け入れ中 | 他者 |
| 11 | 完了 | 完了 |

### 成功条件の測定方法

- 新しいノートを作るたびに、メタデータの欄が揃っているかを確かめる。
- タグのないノートの一覧を開き、空にできるかを確かめる。
- アジェンダを開き、開いているチケットが手番のわかる形で並んでいるかを確かめる。

計測の仕組みは設けない。

### 展開計画

所有者のマシンだけに提供する。
開発環境を「すべて」の範囲で導入すると、すべての要求を使える。
「最小限」の範囲では、要求1と要求4から要求9を使える。要求2、要求3、要求10は、それぞれ補完、一覧、変換の道具が「最小限」に入らないため使えない。
ノートとタスクの保管場所は、所有者が事前に用意する。
段階的な公開はしない。
変更は、各マシンで導入操作をやり直した時点で、そのマシンに反映される。

## 未解決の問い

- ノートのタグを補完することを、要求にするか。
- ノートが増えたときに、ノート全体の関係を俯瞰する方法をどの案で再検討するか。
