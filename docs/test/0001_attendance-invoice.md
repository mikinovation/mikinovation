# テストケース一覧: 勤怠表と請求書の作成

設計書 0001「勤怠表と請求書の作成」の振る舞いを、どの入力と期待値で確かめるかを示す。

- 読者: テストを書く開発者と、仕様との対応を確かめるレビュー担当者
- 前提の PRD: PRD 0007「勤怠表と請求書の作成」
- 前提の設計書: 設計書 0001「勤怠表と請求書の作成」
- ケース ID: `TC-0001-<連番3桁>`。ID は振り直さず、削除したケースは「廃止したケース」に残す
- 照合の方法: リポジトリルートで `check-test-ids --only 0001` を実行する

用語は PRD 0007 と設計書 0001 と同じ意味で使う。

設計書 0001 で層3を書いたコンポーネントは、読み込み、集計、freee 連携である。
単体の階層のケースは、この3つにだけ置く。
打刻の操作、検出、勤怠表、CLI は、層2の外部とのインターフェースとデータの流れから、統合と E2E の階層のケースだけを置く。

## 打刻の操作

### TC-0001-001 当日の見出しがなければ、案件の見出しの下に作って打刻を始める

- 要求: PRD 0007 要求1
- 根拠: 設計書 0001 層2 コンポーネントの責務
- シーム: 打刻の操作
- 階層: 統合
- 技法: 受入条件の例
- 前提: `KINTAI_PROJECT: sample` を持つ案件の見出しがあり、その下に 2026-09-01 の見出しだけがある。今日は 2026-09-02 である
- 操作: 打刻のキー操作を1回行う
- 期待: 案件の見出しの1つ下に、見出しの文字が `2026-09-02` の見出しができ、その見出しの LOGBOOK に終了のない CLOCK 行が1行できる

## 意図して扱わない振る舞い

| 観点 | 理由 |
|---|---|
| 月末の skill が、検出、勤怠表の生成、下書きの作成を順に行い、報告し、止まったときに直すべき箇所を案内すること（PRD 0007 要求13） | skill の振る舞いは Claude の応答に左右され、決まった期待値で自動テストにできない。skill が呼ぶ `kintai` の振る舞いは、CLI と各シームのケースで確かめる。2026年9月分の並行運用で、所有者が確かめる |
| 勤怠表 PDF を freee の画面で請求書に添付して送れること（PRD 0007 要求12 のうち添付の操作） | 所有者が freee の画面で行う手作業である。`kintai` の側は、PDF を決まった場所に書き出すことまでを TC-0001-059 で確かめる |
| 請求書が送付されないこと | freee 連携は送付の手段を持たない（設計書 0001 層2 非機能要求への対応）。送付待ちの請求書を作ることは TC-0001-069 で確かめる |
| 勤怠表 PDF がマシンによらず同じになること | 1つの環境で動くテストでは、マシンの違いを再現できない |
| 勤怠表の見た目の細部 | 設計書 0001 のスコープ外である |
| 時間と金額に浮動小数点数を使わないこと | 振る舞いではなく実装の制約であり、コードのレビューで確かめる。計算の結果は集計のケースで確かめる |
| 実際の freee請求書 API と 1Password を相手にした通信 | 本物の請求書を作り、認証情報が要るため、自動テストにしない。freee の API の trait と `op` を偽物に差し替えて確かめる |
| Home Manager による導入範囲「すべて」への組み込み | 振る舞いのテストではなく、Nix の評価とビルドで確かめる |
| 誤って作った請求書を freee で取消してから作り直せること | 取消は freee の画面での手作業である。取消した請求書を数えない条件は TC-0001-065 で確かめる |
