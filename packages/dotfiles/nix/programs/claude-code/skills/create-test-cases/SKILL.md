# create-test-cases: 振る舞いのテストケース作成スキル

設計書一つに対して、振る舞いのテストケース一覧を一つ作る。このスキルはケースの材料を集め、合意を得てから japanese-review に執筆を渡し、最後にテストコードとの対応を照合する。テストコードは書かない。

文書の役割を次のように分ける。テストケース一覧は PRD と設計書に沿って書き、それらの内容を決め直さない。

| 文書 | 答える問い | 作るスキル |
|---|---|---|
| PRD | 何を、なぜ作るか。何を満たせば受け入れるか | create-prd |
| ADR | どの方式を選ぶか | create-adr |
| 設計書 | 選んだ方式で、どう組むか。どこでテストするか | create-design-doc |
| テストケース一覧 | どの振る舞いを、どの入力と期待値で確かめるか | このスキル |

ケース一覧は自然文で先に作るが、テストコードは tdd で一件ずつ書く。テストコードを先にまとめて書かせない。

## 抜け漏れを防ぐ仕組み

抜け漏れは、次の三つで防ぐ。どれか一つが欠けると防げない。

1. 観点の導出: 思いついたケースを並べず、PRD と設計書の記述ごとにテスト技法を当てはめて観点を導く（手順3）。
2. 網羅の検査: 要求と設計の記述のうち、ケースも「意図して扱わない振る舞い」もないものを、独立した検査で見つける（手順6）。
3. コードとの照合: ケース ID をテスト名に入れ、照合コマンド `check-test-ids` で、すべてのケースにテストがあるかを機械的に確かめる（手順9）。

## テストケース一覧の形式

照合コマンドが読むため、次の形式を崩さない。

- 保存先: リポジトリルートの `docs/test/`。保存先をユーザーに問わない。
- ファイル名: 前提の設計書と同じ `<番号>_<タイトル>.md`。例: 設計書 `docs/design/0001_attendance-invoice.md` に対して `docs/test/0001_attendance-invoice.md`
- ケース ID: `TC-<設計書の番号4桁>-<連番3桁>`。例: `TC-0001-014`
- ケースは見出し一つで表し、見出しは ID で始める。見出しにしたケースには、すべてテストを書く。テストを書かない観点は、ケースの見出しにせず、「意図して扱わない振る舞い」か「未解決点」に置く。

```markdown
### TC-0001-014 始業を切り上げ、終業を切り捨てて丸める

- 要求: PRD 0007 要求6
- 根拠: 設計書 0001 層3 集計
- シーム: 集計
- 階層: 単体
- 技法: 受入条件の例
- 前提: 丸めの単位が15分で、始業を切り上げ、終業を切り捨てる案件がある
- 操作: 始業9:58、終業19:07で打刻した日を集計する
- 期待: 始業は10:00、終業は19:00になる
```

| 項目 | 内容 |
|---|---|
| 要求 | 満たす PRD の要求の番号。要求に直接ひもづかない設計上の振る舞いは「なし」 |
| 根拠 | 観点を導いた設計書の層と節 |
| シーム | テストする境界。設計書の「テストの位置」と、層2のコンポーネントの名前を使う |
| 階層 | 単体、統合、E2E のいずれか |
| 技法 | 観点を導いた技法（手順3の表） |
| 前提、操作、期待 | Given、When、Then にあたる。期待には、仕様から決めた具体的な値を書く |

ID は振り直さない。ケースを削除したら、末尾の「廃止したケース」の節に、ID と理由を箇条書きで残す。新しい ID は、廃止したものも含めた最大の連番に1を足す。

## 手順

### 1. 対象を定める

ユーザーの依頼から、前提とする設計書と、既存のテストケース一覧があるかを確認する。

設計書がない場合は、create-design-doc で先に設計書を作ることを推奨回答として示す。

設計書の到達している層を確かめる。層3を書いていないコンポーネントには、単体の階層のケースを作らず、層2の外部とのインターフェースとデータの流れから、統合と E2E の階層のケースだけを作る。単体のケースが必要なら、そのコンポーネントの層3を create-design-doc で先に加えることを推奨回答として示す。

### 2. 前提の文書とテストを読む

リポジトリルートの `docs/design/` から設計書を、`docs/prd/` から設計書が前提とする PRD を、`docs/test/` から既存のテストケース一覧を読む。ADR は、設計書の「前提とする決定」に挙げたもののうち、振る舞いを制約するものだけを読む。

既存のテストケース一覧を更新する場合は、照合コマンド（手順9）を実行し、現在どのケースにテストがあるかを把握する。

読んだ文書の一覧を示し、過不足がないかを確かめる。これは前提の確認であり、執筆の承認ではない。

### 3. 観点を導く

PRD と設計書の記述を一つずつ取り上げ、次の表で技法を当てはめて観点を導く。記述から導けない観点を補わない。

| 記述 | 技法 | 導く観点 |
|---|---|---|
| PRD の受入条件と、そこに示された例 | 受入条件の例 | 例をそのまま一つのケースにする |
| 値に範囲や区切りがある入力（時刻、金額、件数、期間） | 同値分割、境界値 | 各区間の代表値と、境界の両側。境界ちょうどの値を必ず含める |
| 結果を左右する設定や条件の組み合わせ | デシジョンテーブル | 結果が変わる組み合わせごとに一つ。結果が同じ組み合わせはまとめる |
| 状態と遷移（層3の型と状態） | 状態遷移 | 許される遷移ごとに一つと、許されない遷移を一つ以上 |
| エラーの扱い（層3）、重要な失敗時のデータの流れ（層2） | エラー推測 | エラーの種類ごとに、検出と通知と回復を確かめるケース |
| 外部とのインターフェース（層2） | インターフェースの契約 | 正常な入出力と、不正な入力の拒否 |
| 非機能要求への対応（層2） | 観点の確認 | 自動テストで確かめられるものだけをケースにし、それ以外は意図して扱わない振る舞いに回す |

導いた観点を、根拠の記述と技法とあわせて一覧で示す。観点ごとに、ケースにするか、意図して扱わない振る舞いにするかを推奨回答として添える。

既存のコードやテストを読んで分かる事実（既存のテストの位置、型の名前など）は調べて埋め、根拠として示す。

### 4. 読者を確認する

テストケース一覧の読者は、テストを書く開発者と、仕様との対応を確かめるレビュー担当者である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 5. grilling で期待値を決める

`Skill` ツールで `grilling` を呼び、手順3の観点のうち、文書から決まらないものを詰める。聞くのは次の二つに限る。

- 期待値: 文書に例がない観点の、具体的な期待値。
- 意図して扱わない振る舞い: ケースにしない観点と、その理由。

期待値は、仕様から決めた値にする。実装のコードから逆算した値や、実装と同じ計算式で求めた値を期待値にしない。期待値が仕様から決まらない場合は、設計や要求の不足として扱い、手順7で未解決点に加える。

ユーザーが決まっていないと答えた観点は、ケースにせず、期待値を `TBD` として未解決点に加える。期待値が決まったら、その時点でケースにする。

文書、コード、ユーザーの回答のいずれにもない事実、数値、条件を補わない。

聞き取りの途中で、PRD の要求や設計書の記述と矛盾する振る舞いが見つかった場合は、その場で指摘する。要求の変更は create-prd、設計の変更は create-design-doc を案内し、このスキルの中で決め直さない。

### 6. 網羅を検査する

`Agent` ツールで、聞き取りの経緯を知らない独立したサブエージェントを起こす。サブエージェントには、前提の文書のパスと、ケースの材料の一覧だけを渡し、次を検査させる。

- PRD の受入条件のうち、ケースが一つもないもの
- 設計書のエラーの扱い、状態遷移、外部とのインターフェースの記述のうち、ケースも意図して扱わない振る舞いもないもの
- 範囲のある入力のうち、境界の片側しかケースがないもの
- 期待値が具体的な値になっていないケース、または実装と同じ計算で求めているケース
- 一つのケースが複数の振る舞いを確かめていて、失敗したときに原因を特定できないもの

サブエージェントには、結果を `合格`、`要修正`、`設計へ戻す` のいずれかと、指摘の一覧で返させる。

- `要修正`: 指摘を材料に反映し、もう一度検査する。修正と検査は2回までとする。2回で合格しなければ、残った指摘を未解決点に加えてユーザーに示す。
- `設計へ戻す`: 要求や設計の記述が足りず、ケースを導けない場合である。不足している記述を示し、create-prd か create-design-doc を推奨回答として示す。

### 7. 材料一覧を提示して合意を取る

次を示し、この内容でテストケース一覧を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得る。

- 前提の文書
- ケースの一覧（ID、見出し、要求、シーム、階層）
- 要求ごとのケースの数
- 意図して扱わない振る舞いと理由
- 網羅の検査の結果
- `TBD` の件数と未解決点

### 8. japanese-review に執筆を渡す

`Skill` ツールで `japanese-review` を呼び、依頼を執筆、立場を `決まり` として、確定した材料を渡してテストケース一覧を執筆させる。文書の種類は、振る舞いの仕様を参照するための文書とし、検査の種類には `stock` を指定させる。実行結果や進捗を書く文書ではないため、チェックボックスを含めない。

次の構成と形式を japanese-review に渡す。

- 冒頭: 前提の PRD と設計書、ケース ID の規約、照合の方法を書く。
- 追跡表: PRD の要求ごとに、対応するケースの ID を並べる。
- シームごとの節: 節の見出しをシームの名前にし、その下にケースを並べる。
- 意図して扱わない振る舞い: 観点と理由を書く。
- 未解決点: 期待値が `TBD` の観点と、網羅の検査で残った指摘を書く。
- 廃止したケース: 削除したケースの ID と理由を箇条書きで書く。見出しにしない。
- 出典: 前提の文書を書く。

ケースの形式は「テストケース一覧の形式」のとおりとし、見出しの ID の書き方を変えさせない。文章の推敲で項目名を言い換えさせない。

既存のテストケース一覧を更新する場合は、同じファイルを更新させる。既存のケースの ID を変えさせず、承認なしに期待値を書き換えさせない。

### 9. 照合する

執筆の後、リポジトリルートで照合コマンドを実行し、結果をユーザーに示す。

```sh
check-test-ids --only <設計書の番号>
```

| 引数 | 意味 |
|---|---|
| `--docs <dir>` | テストケース一覧のディレクトリ。既定は `docs/test` |
| `--src <dir>` | テストコードを探すディレクトリ。複数指定できる。既定はリポジトリルート |
| `--only <番号>` | 照合する文書の番号。複数指定できる |
| `--strict` | 文書にない ID がコードにある場合も失敗にする |

`check-test-ids` は Home Manager で導入する Rust のコマンドで、`.md` 以外のファイルから ID を探す。ID はテスト名や文字列の中に次のどの書き方で書いてもよい。

| 言語 | 書き方の例 |
|---|---|
| Rust | `fn tc_0001_014_rounds_start_up()` |
| TypeScript | `test("TC-0001-014 始業を切り上げて丸める", ...)` |
| Lua（busted） | `it("TC-0001-014 始業を切り上げて丸める", ...)` |

終了コードは、0 が合格、1 がテストのないケースがある、または `--strict` で文書にない ID がある、2 が引数か文書の形式の誤りである。2 の場合は、テストケース一覧の形式を直す。

新規作成の直後は、まだテストがないため終了コード1になる。これを失敗として扱わず、これから書くテストの一覧として示す。そのうえで、次を案内する。

- 実装は、`Skill` ツールで `tdd` を呼び、ケースを一件ずつ書く。ケースのシームを、tdd で合意するシームとして使う。テスト名にはケース ID を入れる。
- 照合コマンドを CI に入れると、テストのないケースを、マージの前に検出できる。CI では `cargo install --locked --git https://github.com/mikinovation/mikinovation check-test-ids` で導入する。
- CI では、実装を終えた設計書の番号だけを `--only` で指定する。実装中の文書を照合の対象にすると、テストを書き終えるまで CI が通らない。設計書の実装を終えたら、その番号を CI の `--only` に加えることを案内する。

## このスキルで扱わないこと

- テストコードの実装（tdd の領分）
- 要求と受入条件の決定（PRD の領分）
- 構成、境界、エラーの扱いの決定（設計書の領分）
- 作業の分担と順序（計画の領分。create-plan を使う）
- テストの実行結果と進捗の記録
- テストが誤りを検出できるかの検査（ミューテーションテストの領分）
