# create-design-doc: 設計書作成ヒアリングスキル

設計書の材料を grilling で聞き取り、ユーザーの承認を得てから tanteki に執筆または更新を渡す。このスキルは材料集めだけを行う。

文書の役割を次のように分ける。設計書は PRD と ADR に沿って書き、それらの内容を選び直さない。

| 文書 | 答える問い | 作るスキル |
|---|---|---|
| PRD | 何を、なぜ作るか | create-prd |
| ADR | どの方式を選び、なぜ他の案を採らないか | create-adr |
| 設計書 | 選んだ方式で、どう組むか | このスキル |

設計書は PRD 一つに対して一つ作る。全体の構成とコンポーネントの内部を別の文書に分けず、一つの設計書の中で、上から読み進めるほど詳しくなるように並べる。

## 設計書の層

設計書は次の三つの層からなる。読者は上の層だけを読めば、その深さでの全体像が分かる。下の層は上の層の内容を前提にし、上の層の記述を覆さない。

| 層 | 読む人の例 | 答える問い | 項目 |
|---|---|---|---|
| 1. 概要 | 設計を初めて読む人、レビュー担当者 | 何のために、何を前提に、どんな形で作るか | 目的、スコープとスコープ外、前提とする決定、全体の構成 |
| 2. 構成 | 設計の全体を理解して変更する人 | コンポーネントがどう協調し、外からどう見えるか | コンポーネントの責務、データの流れ、外部とのインターフェース、論理データモデル、非機能要求への対応 |
| 3. コンポーネント | そのコンポーネントを実装、保守する人 | 一つのコンポーネントの内部をどう組むか | モジュールの分割とインターフェース、型と状態、エラーの扱い、物理データ形式、テストの位置 |

層3は、判断が込み入るコンポーネントにだけ書く。コードとテストを読めば分かる内容しかないコンポーネントには書かない。

影響とリスク、未解決点、出典は層に属さず、設計書の末尾にまとめる。各項目には、どの層のどの記述に関わるかを示す。

設計書は一度で全層を書き切らなくてよい。層1と層2を先に書き、層3は実装の前に必要になったコンポーネントから同じ設計書に加える。

## 手順

### 1. 対象と到達させる層を定める

ユーザーの依頼から、前提とする PRD と、既存の設計書があるかを確認する。

新規作成では、層2までを到達点とすることを推奨回答として示す。既存の設計書を更新する場合は、その設計書を読んで現在の到達点を把握し、次に加える層、または層3を加えるコンポーネントを推奨回答として示す。ユーザーが異なる到達点を指定した場合はそれに従う。

到達させる層より下の層の項目は聞かない。それらは `TBD` ではなく未着手として扱う。

PRD がない場合は、create-prd で先に PRD を作ることを推奨回答として示す。ユーザーが PRD なしで進めると答えた場合は、目的とスコープを手順5で聞き取る。

### 2. 前提の文書を読む

リポジトリルートの `docs/prd/`、`docs/adr/`、`docs/design/` から、手順1で定めた PRD と既存の設計書、対象に関係する ADR を読む。関係するかどうかは、ADR の題名と背景で判断する。

ADR は状態が「採用」のものを前提とし、「提案」のものは未確定の前提として扱う。「廃止」「置換」の ADR は前提にせず、置き換えた ADR を読む。

読んだ文書の一覧を、前提として採るかどうかとあわせて示し、過不足がないかを確かめる。これは前提の確認であり、執筆の承認ではない。

### 3. ADR で決まっていない論点を洗い出す

PRD の要求、または設計書の既存の構成を実現するために必要な方式上の決定を挙げ、それぞれを ADR が決めているかを照合する。

次のいずれかに当たる決定は ADR の領分とする。

- 言語、ライブラリ、外部サービス、データの保存方式など、技術や方式を選ぶ
- 複数のコンポーネント、または他の PRD の機能に影響する
- 後から変えるには大きな手戻りがある

ADR がない論点が見つかった場合は、その一覧を示し、設計の聞き取りを止めて create-adr で ADR を作ることを推奨回答として示す。ユーザーが ADR を作らずに進めると答えた論点は、未解決点として手順5の材料に加え、設計書の中で方式を決めない。

これに当たらない、一つのコンポーネントに閉じた小さな選択は、設計書の中で理由とあわせて決めてよい。

### 4. 読者を確認する

設計書の読者は開発者、レビュー担当者、将来の保守者である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 5. grilling を層ごとに行う

到達させる層までの未確定の項目を、層ごとに `Skill` ツールで `grilling` を呼んで詰める。上の層が合意されるまで、下の層の項目を聞かない。手順2の文書で埋まっている項目は飛ばし、飛ばしたことをユーザーに伝える。

| 層 | 項目 | 何のために聞くか |
|---|---|---|
| 1. 概要 | 目的 | PRD のどの要求を満たす設計かを示す |
| | スコープとスコープ外 | 設計で扱う範囲と扱わない範囲を限る |
| | 前提とする決定 | 従う ADR と、その決定が設計をどう制約するかを示す |
| | 全体の構成 | どのコンポーネントからなるかを、一目で分かる形で示す |
| 2. 構成 | コンポーネントの責務 | 各コンポーネントが何を受け持ち、何を受け持たないかを定める |
| | データの流れ | 通常時と重要な失敗時に、データがコンポーネントの間をどう流れるかを示す |
| | 外部とのインターフェース | 利用者や外部のシステムから見える入出力（コマンド、API、画面、ファイル）を定める |
| | 論理データモデル | 扱うデータの実体、属性の意味、関係を定める |
| | 非機能要求への対応 | 性能、可用性、保守性、安全性の要求を、構成のどこで満たすかを示す |
| 3. コンポーネント | モジュールの分割とインターフェース | 外から呼ばれる入口を小さく保ち、どこに境界を置くかを定める |
| | 型と状態 | 扱うデータの型と、状態の遷移を定める |
| | エラーの扱い | エラーの種類ごとに、検出、通知、回復のしかたを定める |
| | 物理データ形式 | 保存や入出力に使う形式（テーブル、ファイル形式、スキーマなど）を定める |
| | テストの位置 | どの境界で振る舞いを確かめるか、既存のどのテストにならうかを示す |
| 末尾 | 影響とリスク | 採用で何が変わり、どこまで影響し、元に戻せるかを示す |
| | 未解決点 | 採否や実装を左右する未確認事項と、手順3で残った論点を残す |
| | 出典 | 各主張の根拠となる原資料 |

層3は、層2で挙げたコンポーネントのうち、ユーザーが選んだものについてだけ聞く。選ぶ際は、判断が込み入るかどうかを根拠に、対象とするコンポーネントを推奨回答として示す。末尾の項目は、到達させる層の内容に関わる範囲で、最後の層の grilling に含める。

各層の終わりに、その層の結論を短くまとめて示し、修正がないことを確かめてから次の層へ進む。これは層の結論の確認であり、執筆の承認ではない。下の層で上の層の結論と矛盾が見つかった場合は、上の層に戻って詰め直す。

grilling は、環境を調べてわかる事実は調べて埋め、決定はユーザーに委ねる。このスキルでは、この区別を次のように当てはめる。

- 既存のコードの構成、型、テストのように、リポジトリを読めばわかる事実は調べて埋める。調べた事実は推奨回答の根拠として示す。
- 構成、境界、エラーの扱いなど、これから決めることはユーザーに確かめる。

grilling が求める推奨回答は、提案であると明示する。ユーザーが承認するまで材料に書き込まない。前提の文書、コード、ユーザーの回答のいずれにもない事実、数値、条件を補わない。

聞き取りの途中で、ADR の決定と矛盾する案や、手順3の基準で ADR の領分に当たる論点が出た場合は、その場で指摘する。ADR を選び直す必要があれば、設計の聞き取りを止めて create-adr で新しい ADR を作ることを推奨回答として示す。既存の ADR を書き換えさせない。

ユーザーが決まっていないと答えた項目は、考えさせ続けずに `TBD` とし、未解決点に加えて次へ進む。ただし「全体の構成」が `TBD` のままでは設計書が成立せず、層3では「モジュールの分割とインターフェース」が `TBD` のままではそのコンポーネントの記述が成立しないため、それが定まるまで手順7へ進まない。

### 6. 材料一覧を提示して合意を取る

到達させる層、前提とする文書、全項目の一覧（確定、`TBD`、未着手の別）、層3を書くコンポーネント、`TBD` の件数、未解決点を示す。この内容で設計書を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順7へ進む。

### 7. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料と到達させる層を渡して設計書を執筆させる。文書の種類は Design Doc とし、検査の種類には `design-doc` を指定させる。

設計書を段階的に読めるようにするため、次のことを tanteki に渡す。

- 層1、層2、層3の順に並べ、末尾に影響とリスク、未解決点、出典を置く。
- 冒頭で、層ごとにどこまで読めば何が分かるかを示し、読者が必要な深さで読み止められるようにする。
- 各層は、その層までの記述だけで意味が通るように書く。下の層の用語や内容を、上の層で先に使わない。
- 層3は、コンポーネントごとにまとめ、層2のどのコンポーネントを詳しくしたものかを示す。
- 全体の構成とデータの流れは、図が理解を助ける場合に Mermaid で示す。
- 現在どの層まで書いたかと、層3を書いたコンポーネントを冒頭に記載する。未着手の層と項目は設計書に含めない。

方式の比較については、次のことを tanteki に渡す。tanteki の Design Doc は採用案と代替案の比較を求めるが、このスキルの設計書では方式の比較を ADR に任せる。

- 方式を選んだ理由は、前提とする ADR を参照して示す。ADR の決定を一文で要約し、代替案の比較は本文に繰り返さない。
- 手順3で設計書の中で決めた小さな選択は、その理由を本文に書く。
- 設計書は前提の PRD を参照する。
- リポジトリのファイルパスとコードの断片は本文に含めない。型や状態遷移のように、文章より正確に決定を表せるものは、決定に必要な部分だけを示してよい。

設計書の保存先は、どのリポジトリでもリポジトリルートの `docs/design/` に固定する。保存先をユーザーに問わず、tanteki にも渡す。

新規の設計書のファイル名は `<番号>_<タイトル>.md` とし、この規則も tanteki に渡す。番号は保存先ディレクトリにある既存の設計書の最大番号に 1 を足した4桁のゼロ埋め（最初は `0001`）とする。タイトルは設計の対象を表す英小文字の語とし、複数語はハイフンでつなぐ。例: `0001_attendance-invoice.md`

既存の設計書を更新する場合は、同じファイルを更新させ、新しいファイルを作らない。上の層で確定した記述を、ユーザーの承認なしに書き換えさせない。前提の ADR が置き換えられた場合は、参照を新しい ADR に改め、置き換えで変わる記述をユーザーに確かめてから更新させる。

## このスキルで扱わないこと

- 見出しの文言と本文の表現
- textlint による検査と合格判定
- 要求と成功条件の決定（PRD の領分）
- 方式の選定と代替案の比較（ADR の領分）
- 作業の分担と進捗、PR 番号、課題ID（計画、チケットの領分。計画は create-plan を使う）
