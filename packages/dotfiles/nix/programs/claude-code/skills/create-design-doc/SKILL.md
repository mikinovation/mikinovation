# create-design-doc: 設計書作成ヒアリングスキル

設計書の材料を grilling で聞き取り、ユーザーの承認を得てから tanteki に執筆を渡す。このスキルは材料集めだけを行う。

文書の役割を次のように分ける。設計書は PRD と ADR に沿って書き、それらの内容を選び直さない。

| 文書 | 答える問い | 作るスキル |
|---|---|---|
| PRD | 何を、なぜ作るか | create-prd |
| ADR | どの方式を選び、なぜ他の案を採らないか | create-adr |
| 基本設計 | 選んだ方式で、全体をどう組むか | このスキル |
| 詳細設計 | 基本設計の一つのコンポーネントを、内部でどう組むか | このスキル |

## 設計の水準

| 水準 | 対象 | 前提とする文書 | 決めること |
|---|---|---|---|
| 基本設計 | PRD 一つが求める機能の全体 | PRD、関係する ADR | 構成、コンポーネントの責務、データの流れ、外部とのインターフェース、論理データモデル |
| 詳細設計 | 基本設計にあるコンポーネント一つ | 基本設計書、関係する ADR | モジュールの分割とインターフェース、型と状態、エラーの扱い、物理データ形式、テストの位置 |

詳細設計は、判断が込み入るコンポーネントにだけ書く。コードとテストを読めば分かる内容しかないコンポーネントには書かない。

## 手順

### 1. 水準と対象を定める

ユーザーの依頼から、基本設計と詳細設計のどちらを書くかと、その対象を判定し、推奨回答として示す。

基本設計では、前提とする PRD を一つ確認する。PRD がない場合は、create-prd で先に PRD を作ることを推奨回答として示す。ユーザーが PRD なしで進めると答えた場合は、目的とスコープを手順5で聞き取る。

詳細設計では、親となる基本設計書と、対象のコンポーネントを確認する。基本設計書がない場合は、先に基本設計を書くことを推奨回答として示す。対象のコンポーネントが、コードとテストを読めば分かる内容しかない場合は、詳細設計を書かないことを推奨回答として示す。

### 2. 前提の文書を読む

リポジトリルートの `docs/prd/`、`docs/adr/`、`docs/design/` から、手順1で定めた PRD または基本設計書と、対象に関係する ADR と設計書を読む。関係するかどうかは、ADR の題名と背景で判断する。

ADR は状態が「採用」のものを前提とし、「提案」のものは未確定の前提として扱う。「廃止」「置換」の ADR は前提にせず、置き換えた ADR を読む。

読んだ文書の一覧を、前提として採るかどうかとあわせて示し、過不足がないかを確かめる。これは前提の確認であり、執筆の承認ではない。

### 3. ADR で決まっていない論点を洗い出す

PRD の要求、または基本設計の構成を実現するために必要な方式上の決定を挙げ、それぞれを ADR が決めているかを照合する。

次のいずれかに当たる決定は ADR の領分とする。

- 言語、ライブラリ、外部サービス、データの保存方式など、技術や方式を選ぶ
- 複数のコンポーネント、または他の PRD の機能に影響する
- 後から変えるには大きな手戻りがある

ADR がない論点が見つかった場合は、その一覧を示し、設計の聞き取りを止めて create-adr で ADR を作ることを推奨回答として示す。ユーザーが ADR を作らずに進めると答えた論点は、未解決点として手順5の材料に加え、設計書の中で方式を決めない。

これに当たらない、一つのコンポーネントに閉じた小さな選択は、設計書の中で理由とあわせて決めてよい。

### 4. 読者を確認する

設計書の読者は開発者、レビュー担当者、将来の保守者である。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 5. grilling で水準ごとの項目を詰める

`Skill` ツールで `grilling` を呼び、水準に応じた次の項目を論点として詰める。前提となる項目が決まるまで、それに依存する項目は後のラウンドに回す。手順2の文書で埋まっている項目は飛ばし、飛ばしたことをユーザーに伝える。

基本設計の項目:

| # | 項目 | 何のために聞くか |
|---|---|---|
| 1 | 目的 | PRD のどの要求を満たす設計かを示す |
| 2 | スコープとスコープ外 | 設計で扱う範囲と扱わない範囲を限る |
| 3 | 前提とする決定 | 従う ADR と、その決定が設計をどう制約するかを示す |
| 4 | 全体の構成 | コンポーネントと、それぞれの責務を定める |
| 5 | データの流れ | 通常時と重要な失敗時に、データがコンポーネントの間をどう流れるかを示す |
| 6 | 外部とのインターフェース | 利用者や外部のシステムから見える入出力（コマンド、API、画面、ファイル）を定める |
| 7 | 論理データモデル | 扱うデータの実体、属性の意味、関係を定める |
| 8 | 非機能要求への対応 | 性能、可用性、保守性、安全性の要求を、構成のどこで満たすかを示す |
| 9 | 影響とリスク | 採用で何が変わり、どこまで影響し、元に戻せるかを示す |
| 10 | 未解決点 | 設計の採否を左右する未確認事項と、手順3で残った論点を残す |
| 11 | 出典 | 各主張の根拠となる原資料 |

詳細設計の項目:

| # | 項目 | 何のために聞くか |
|---|---|---|
| 1 | 目的 | 基本設計のどのコンポーネントを、どこまで詳しくするかを示す |
| 2 | 前提とする決定 | 親の基本設計書と、従う ADR を示す |
| 3 | モジュールの分割とインターフェース | 外から呼ばれる入口を小さく保ち、どこに境界を置くかを定める |
| 4 | 型と状態 | 扱うデータの型と、状態の遷移を定める |
| 5 | 処理の流れ | 通常時の処理の順序を示す |
| 6 | エラーの扱い | エラーの種類ごとに、検出、通知、回復のしかたを定める |
| 7 | 物理データ形式 | 保存や入出力に使う形式（テーブル、ファイル形式、スキーマなど）を定める |
| 8 | テストの位置 | どの境界で振る舞いを確かめるか、既存のどのテストにならうかを示す |
| 9 | 影響とリスク | 他のコンポーネントや既存のデータへの影響と、元に戻せるかを示す |
| 10 | 未解決点 | 実装の前に答えるべき問いを残す |
| 11 | 出典 | 各主張の根拠となる原資料 |

grilling は、環境を調べてわかる事実は調べて埋め、決定はユーザーに委ねる。このスキルでは、この区別を次のように当てはめる。

- 既存のコードの構成、型、テストのように、リポジトリを読めばわかる事実は調べて埋める。調べた事実は推奨回答の根拠として示す。
- 構成、境界、エラーの扱いなど、これから決めることはユーザーに確かめる。

grilling が求める推奨回答は、提案であると明示する。ユーザーが承認するまで材料に書き込まない。前提の文書、コード、ユーザーの回答のいずれにもない事実、数値、条件を補わない。

聞き取りの途中で、ADR の決定と矛盾する案や、手順3の基準で ADR の領分に当たる論点が出た場合は、その場で指摘する。ADR を選び直す必要があれば、設計の聞き取りを止めて create-adr で新しい ADR を作ることを推奨回答として示す。既存の ADR を書き換えさせない。

ユーザーが決まっていないと答えた項目は、考えさせ続けずに `TBD` とし、未解決点に加えて次へ進む。ただし基本設計では「全体の構成」、詳細設計では「モジュールの分割とインターフェース」が `TBD` のままでは設計書が成立しないため、それが定まるまで手順7へ進まない。

### 6. 材料一覧を提示して合意を取る

水準、前提とする文書、全項目の一覧、`TBD` の件数、未解決点を示す。この内容で設計書を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得て、その承認をもって手順7へ進む。

### 7. tanteki に執筆を渡す

`Skill` ツールで `tanteki` を呼び、確定した材料と水準を渡して設計書を執筆させる。文書の種類は Design Doc とし、検査の種類には `design-doc` を指定させる。

tanteki の Design Doc は採用案と代替案の比較を求めるが、このスキルの設計書では方式の比較を ADR に任せる。次のことを tanteki に渡す。

- 方式を選んだ理由は、前提とする ADR を参照して示す。ADR の決定を一文で要約し、代替案の比較は本文に繰り返さない。
- 手順3で設計書の中で決めた小さな選択は、その理由を本文に書く。
- 基本設計書は PRD を、詳細設計書は親の基本設計書を参照する。
- 図が理解を助ける場合は、Mermaid で構成やデータの流れを示す。
- リポジトリのファイルパスとコードの断片は本文に含めない。型や状態遷移のように、文章より正確に決定を表せるものは、決定に必要な部分だけを示してよい。

設計書の保存先は、どのリポジトリでもリポジトリルートの `docs/design/` に固定する。保存先をユーザーに問わず、tanteki にも渡す。

設計書のファイル名は `<番号>_<タイトル>.md` とし、この規則も tanteki に渡す。番号は保存先ディレクトリにある既存の設計書の最大番号に 1 を足した4桁のゼロ埋め（最初は `0001`）とし、基本設計と詳細設計で同じ番号の系列を使う。タイトルは設計の対象を表す英小文字の語とし、複数語はハイフンでつなぐ。詳細設計では、タイトルの末尾に対象のコンポーネント名を付ける。例: `0001_attendance-invoice.md`、`0002_attendance-invoice-aggregation.md`

既存の設計書を更新する場合は、同じファイルを更新させ、新しいファイルを作らない。前提の ADR が置き換えられた場合は、参照を新しい ADR に改め、置き換えで変わる記述をユーザーに確かめてから更新させる。

## このスキルで扱わないこと

- 節構成、見出し、本文の表現
- textlint による検査と合格判定
- 要求と成功条件の決定（PRD の領分）
- 方式の選定と代替案の比較（ADR の領分）
- 作業の分担と進捗、PR 番号、課題ID（計画、チケットの領分）
