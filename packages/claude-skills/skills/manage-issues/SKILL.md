# manage-issues: issue 管理スキル

`apps/docs-hub/src/content/issues.yaml` の issue を記録し、状態を進める。見つけた改善案は承認待ちとして記録し、所有者が承認した issue だけを上から順に進める。承認済みの issue には、着手の前に決めることを候補と推奨案の形で並べた論点を持たせる。

キー、採番、状態の進み方、優先度の表し方、公開してよい内容の決まりは、このスキルには写さない。正本は次の4か所である。

| 読む場所 | 何が書いてあるか |
|---|---|
| `apps/docs-hub/README.md` の「issue」節 | キー、採番、状態、優先度、公開してよい内容、論点の置き場所 |
| `apps/docs-hub/src/lib/issues-schema.ts` | issue の形の検査の規則 |
| `apps/docs-hub/src/lib/grillings-schema.ts` | 論点の形の検査の規則 |
| `apps/docs-hub/src/lib/repositories.ts` | `repository` に書ける ID |

書き換える対象は `apps/docs-hub/src/content/issues.yaml` と `apps/docs-hub/src/content/grillings/<id>.yaml` だけである。コミットと PR は所有者が決めるため、このスキルはファイルを書き換え、変えた内容を伝えたところで終える。

検査にはこのスキルのスクリプトを使う。リポジトリのルートで実行する。

```sh
node packages/claude-skills/skills/manage-issues/scripts/check-issues.mjs
```

写しや別の場所の YAML を検査するときは、そのパスを引数で渡す。省くと `apps/docs-hub/src/content/issues.yaml` を検査する。論点の YAML は引数に関わらず `apps/docs-hub/src/content/grillings` を見る。

## 手順

### 1. 現状を読む

スクリプトを実行し、次の id、各状態の件数、既存の issue の一覧、論点の件数を得る。一覧の4列目は論点の問数で、`-` は論点がない issue である。最後の行には、論点がない承認済み issue の id が並ぶ。

終了コードが0なら先へ進む。1なら、自分が書き換える前から形が正しくない。出力に示された箇所を所有者に伝え、直すかどうかを確かめる。2なら、mikinovation リポジトリの中で実行しているか、`apps/docs-hub` で `pnpm install` を済ませているか、引数に渡したパスが実在するかを確かめる。

あわせて `apps/docs-hub/README.md` の「issue」節を読む。

完了条件: 次の id、`doing` の件数、既存の issue のタイトル、論点がない承認済み issue の id を把握している。

### 2. 依頼を仕分ける

依頼を次の6つのどれか1つに決める。複数を含む依頼は分けて順に行う。

| 仕分け | 当たる依頼 | 進む先 |
|---|---|---|
| 追加 | 改善案を記録する | 手順3 |
| 状態の更新 | 承認を反映する、着手する、完了にする、状態を戻す | 手順4、手順7 |
| 論点出し | 承認済みの issue の論点を出す | 手順5 |
| 決定の記録 | 論点のどれかを所有者が選んだと伝えてきた | 手順6 |
| 報告 | 一覧や次の1件を聞かれた | 手順8 |
| 範囲外 | 「このスキルで扱わないこと」に当たる | 手順8で、扱わないことと行き先を伝えて終える |

「扱わないこと」に当たる依頼は、所有者がその場の作業として指示したものでも範囲外とする。それ以外の依頼で、所有者がその場の作業そのものを指示したとき（例「README を書き直して」）は、issue を作らずそのまま実行する。issue に記録するのは、AI が自分で見つけた改善案と、所有者が記録を求めた案である。

完了条件: 6つのうちどれを行うかが決まっている。

### 3. 改善案を追加する

載せるかどうかを先に判定する。このサイトは公開されているため、顧客名、非公開の案件の内容、認証情報に触れる案は載せず、会話で伝える。手順1の一覧に同じ対象を指す issue があるときは追加せず、既存の id を示す。

issue 1件は次の形で書く。`id` は引用符で囲んだ文字列にする。

```yaml
  - id: '0022'
    title: 経歴ページの肩書きを最新の職務に合わせる
    status: proposed
    repository: mikinovation
```

`title` は何をするかが分かる動詞で終える1行にする。字数の上限はスクリプトの検査に任せ、超えたら短く書き直す。`repository` は、1つのリポジトリの作業ならその ID を書き、複数のリポジトリにまたがる作業とどのリポジトリにも属さない作業は `common` にする。`apps/` と `packages/` を含むこのモノレポの作業は `mikinovation` である。

差し込む位置は、次の4つの観点のうち、その案が当たるものを選んで決める。上にあるほど優先度が高いものとする。

1. 公開しているページと README の誤り、動かない表示と機能
2. 記録と実装のずれ
3. 検査の穴
4. 整備と見た目

どの観点にも当たらない案は、位置を所有者に確かめる。

観点は issue の値として持たないため、既存の issue の観点はタイトルから読み取る。`status` が同じ issue を上から読み、追加する案より優先度が低いと判断した最初の issue を見つけ、その直前に入れる。最後まで見つからなければ、同じ状態の最後に入れる。

書き換えたらスクリプトで検査する。スクリプトは形だけを見て、並び順は検査しない。

完了条件: スクリプトが終了コード0で終わっている。あわせて、同じ `status` の中で、追加した issue の直前の issue の優先度が同じか高く、直後の issue の優先度が同じか低いことを、自分で読んで確かめている。

### 4. 状態を進める

指示された issue の状態によって扱いが分かれる。いずれの扱いでも優先度の位置は動かさない。

`proposed` の issue に着手を指示されたときは、`issues.yaml` を書き換えない。承認を求め、代わりに `todo` の最上段を示す。`doing` の issue が既にあるときは、承認すると `doing` が2件になることを添える。完了条件は、ファイルが変わっていないことと、承認を求めたことである。

所有者が承認したと伝えたときは、`status` を `proposed` から `todo` に変える。承認の判断は所有者が行い、このスキルは記録だけを担う。書き換えたら、その issue について続けて手順5を行う。

`todo` のときは、`status` を `doing` に変える。指示がないときは最上段の issue を選ぶ。指示された issue が最上段でないときは、上にある issue を先に進めなくてよいかを所有者に確かめる。`doing` の issue が既にあるときは、先に終えるか切り替えるかを所有者に確かめてから書き換える。README では `doing` は1件までが目安であるが、このスキルでは2件以上になる書き換えを所有者に確かめる。完了条件は、書き換えたあとスクリプトが終了コード0で終わり、`doing` が1件になっていることである。

既に `doing` のときは、書き換えずに着手中であることを伝える。`done` のときは、完了済みであることを伝え、新しい issue として記録するかを確かめる。`doing` を `todo` へ戻す指示は、そのまま書き換える。取り下げの指示は、当てはまる状態がないため扱いを所有者に確かめる。

### 5. 論点を出す

対象は、`status` が `todo` か `doing` で、`apps/docs-hub/src/content/grillings/<id>.yaml` がない issue である。手順1の最後の行に並んだ id がそれに当たる。ファイルが既にある issue は走らせない。上書きは所有者が明示したときだけ行う。

走らせる前に、issue ごとに次を確かめる。

- `repository` が `mikinovation` のときは、このリポジトリを調査対象にする
- それ以外のときは `~/ghq/github.com/mikinovation/<repository>` を探し、あればそのパスを調査対象にする。なければ走らせず、手元にないことを手順8で伝える
- `repository` が `common` のときは、このリポジトリを調査対象にする

対象の issue 1件につきサブエージェント（`general-purpose`）を1つ起動する。同時に走らせるのは最大4件で、5件以上あるときは分けて起動する。論点を書いた YAML はサブエージェントが自分で書き、親はその後に検査する。

サブエージェントには次を渡す。角かっこの中は実際の値に置き換える。

```
issue [id]「[title]」の論点を出し、YAML に書く。調査対象は [調査対象のパス] である。

1. 調査対象のコードと、apps/docs-hub/README.md、apps/docs-hub/src/content/index.ts の索引から、
   この issue に関わる文書とコードを自分で探して読む。
2. 着手の前に所有者が決めることを3〜6問に絞る。問いは、読めば候補のどれかを選べる具体のものにする。
   前提が未定のまま枝分かれする問いは出さず、推奨案を採ったときだけ開く論点は followUp に1つだけ書く。
3. apps/docs-hub/src/lib/grillings-schema.ts の形に従い、
   apps/docs-hub/src/content/grillings/[id].yaml を新しく書く。generatedAt は今日の日付にする。
   options は2〜5個、1問につき推奨案を必ず1つ書く。decision は書かない。

制約として、このサイトは公開されているため、顧客名、非公開の案件の内容、認証情報に触れる内容は書かない。
絵文字と太字は使わず、である調で書き、1項目は1行に収める。所有者の回答は得られないため、質問を投げ返さない。
論点が出せなかったときは、ファイルを作らず理由を返す。
```

全部のサブエージェントが戻ったらスクリプトを1回実行する。形の誤りは親が直す。論点が出せなかった issue は、ファイルを作らずに手順8で理由を伝える。

完了条件: スクリプトが終了コード0で終わり、走らせた issue の論点の問数が一覧に出ている。

### 6. 決定を記録する

所有者が論点のどれかを選んだと伝えてきたときは、その質問の `decision` に、選んだ候補の内容を1行で書く。推奨案のとおりなら `recommendation` と同じ内容を写す。質問は消さず、ほかの質問も残す。

決定を書いたあと所有者が着手を指示したときは、手順4で `doing` に進める。

完了条件: スクリプトが終了コード0で終わり、一覧の決定の件数が増えている。

### 7. 完了にする

その issue に書いた作業の PR がマージされたときに、`status` を `done` に変える。マージは所有者の申告か `gh pr view <番号> --json state` で確かめる。PR の状態を読むことは、扱わないことに挙げた GitHub Issues の操作には当たらない。issue は消さず、位置も動かさない。論点の YAML も消さずに残す。

完了条件: 書き換えたあとスクリプトが終了コード0で終わり、対象の issue が `done` になっている。

### 8. 報告する

書き換えた issue の id と変わった状態、スクリプトの結果を1行で伝える。`proposed` を追加したときは、承認を待つことを添える。論点を出したときは、issue ごとの問数と詳細ページのパス（`/issues/<id>`）を伝える。手順2で範囲外と決めたときは、このスキルでは扱わないことと、下の表の行き先を伝える。

完了条件: 書き換えた issue の id と状態、または範囲外と判断した理由を伝えている。

## このスキルで扱わないこと

| 扱わないこと | 行き先 |
|---|---|
| 承認の判断 | 所有者が決める |
| 論点に対する決定そのもの | 所有者が決め、このスキルは手順6で書き留める |
| issue に書いた作業の実装 | 通常の作業として進める |
| 作業の分割と依存関係の管理 | 組み方は設計書に書く（`create-design-doc`）。着手の順序は実装時に決める |
| 改善案を探す調査 | 通常の作業として調べ、見つけた案を手順3で記録する |
| ADR と PRD の更新 | `create-adr`、`create-prd` |
| 一覧ページ（`/issues`）と詳細ページの表示、検査の規則の変更 | docs-hub の通常の作業として直す |
| コミット、push、PR | `create-pr` |
| GitHub Issues の操作 | 扱わない |
