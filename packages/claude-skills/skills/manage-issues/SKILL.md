# manage-issues: issue 管理スキル

`apps/docs-hub/src/content/issues.yaml` の issue を記録し、状態を進める。見つけた改善案は承認待ちとして記録し、所有者が承認した issue だけを上から順に進める。

キー、採番、状態の進み方、優先度の表し方、公開してよい内容の決まりは、このスキルには写さない。正本は次の3か所である。

| 読む場所 | 何が書いてあるか |
|---|---|
| `apps/docs-hub/README.md` の「issue」節 | キー、採番、状態、優先度、公開してよい内容 |
| `apps/docs-hub/src/lib/issues-schema.ts` | 形の検査の規則 |
| `apps/docs-hub/src/lib/repositories.ts` | `repository` に書ける ID |

書き換える対象は `apps/docs-hub/src/content/issues.yaml` だけである。コミットと PR は所有者が決めるため、このスキルはファイルを書き換え、変えた内容を伝えたところで終える。

検査にはこのスキルのスクリプトを使う。リポジトリのルートで実行する。

```sh
node packages/claude-skills/skills/manage-issues/scripts/check-issues.mjs
```

写しや別の場所の YAML を検査するときは、そのパスを引数で渡す。省くと `apps/docs-hub/src/content/issues.yaml` を検査する。

## 手順

### 1. 現状を読む

スクリプトを実行し、次の id、各状態の件数、既存の issue の一覧を得る。

終了コードが0なら先へ進む。1なら、自分が書き換える前から形が正しくない。出力に示された箇所を所有者に伝え、直すかどうかを確かめる。2なら、mikinovation リポジトリの中で実行しているか、`apps/docs-hub` で `pnpm install` を済ませているか、引数に渡したパスが実在するかを確かめる。

あわせて `apps/docs-hub/README.md` の「issue」節を読む。

完了条件: 次の id、`doing` の件数、既存の issue のタイトルを把握している。

### 2. 依頼を仕分ける

依頼を次の4つのどれか1つに決める。複数を含む依頼は分けて順に行う。

| 仕分け | 当たる依頼 | 進む先 |
|---|---|---|
| 追加 | 改善案を記録する | 手順3 |
| 状態の更新 | 承認を反映する、着手する、完了にする、状態を戻す | 手順4、手順5 |
| 報告 | 一覧や次の1件を聞かれた | 手順6 |
| 範囲外 | 「このスキルで扱わないこと」に当たる | 手順6で、扱わないことと行き先を伝えて終える |

「扱わないこと」に当たる依頼は、所有者がその場の作業として指示したものでも範囲外とする。それ以外の依頼で、所有者がその場の作業そのものを指示したとき（例「README を書き直して」）は、issue を作らずそのまま実行する。issue に記録するのは、AI が自分で見つけた改善案と、所有者が記録を求めた案である。

完了条件: 4つのうちどれを行うかが決まっている。

### 3. 改善案を追加する

載せるかどうかを先に判定する。このサイトは公開されているため、顧客名、非公開の案件の内容、認証情報に触れる案は載せず、会話で伝える。手順1の一覧に同じ対象を指す issue があるときは追加せず、既存の id を示す。

issue 1件は次の形で書く。`id` は引用符で囲んだ文字列にする。

```yaml
  - id: '0022'
    title: 経歴ページの肩書きを最新の職務に合わせる
    status: proposed
    repository: mikinovation
```

`title` は何をするかが分かる動詞で終える1行にする。字数の上限はスクリプトの検査に任せ、超えたら短く書き直す。`repository` は、1つのリポジトリの作業ならその ID を書き、複数のリポジトリにまたがる作業とどのリポジトリにも属さない作業は `common` にする。`apps/` と `packages/` を含むこのモノレポの作業は `mikinovation` である。

差し込む位置は、次の4つの観点のうち、その案が当たるものを選んで決める。上にあるほど優先度が高いものとする。

1. 公開しているページと README の誤り、動かない表示と機能
2. 記録と実装のずれ
3. 検査の穴
4. 整備と見た目

どの観点にも当たらない案は、位置を所有者に確かめる。

観点は issue の値として持たないため、既存の issue の観点はタイトルから読み取る。`status` が同じ issue を上から読み、追加する案より優先度が低いと判断した最初の issue を見つけ、その直前に入れる。最後まで見つからなければ、同じ状態の最後に入れる。

書き換えたらスクリプトで検査する。スクリプトは形だけを見て、並び順は検査しない。

完了条件: スクリプトが終了コード0で終わっている。あわせて、同じ `status` の中で、追加した issue の直前の issue の優先度が同じか高く、直後の issue の優先度が同じか低いことを、自分で読んで確かめている。

### 4. 状態を進める

指示された issue の状態によって扱いが分かれる。いずれの扱いでも優先度の位置は動かさない。

`proposed` の issue に着手を指示されたときは、`issues.yaml` を書き換えない。承認を求め、代わりに `todo` の最上段を示す。`doing` の issue が既にあるときは、承認すると `doing` が2件になることを添える。完了条件は、ファイルが変わっていないことと、承認を求めたことである。

所有者が承認したと伝えたときは、`status` を `proposed` から `todo` に変える。承認の判断は所有者が行い、このスキルは記録だけを担う。

`todo` のときは、`status` を `doing` に変える。指示がないときは最上段の issue を選ぶ。指示された issue が最上段でないときは、上にある issue を先に進めなくてよいかを所有者に確かめる。`doing` の issue が既にあるときは、先に終えるか切り替えるかを所有者に確かめてから書き換える。README では `doing` は1件までが目安であるが、このスキルでは2件以上になる書き換えを所有者に確かめる。完了条件は、書き換えたあとスクリプトが終了コード0で終わり、`doing` が1件になっていることである。

既に `doing` のときは、書き換えずに着手中であることを伝える。`done` のときは、完了済みであることを伝え、新しい issue として記録するかを確かめる。`doing` を `todo` へ戻す指示は、そのまま書き換える。取り下げの指示は、当てはまる状態がないため扱いを所有者に確かめる。

### 5. 完了にする

その issue に書いた作業の PR がマージされたときに、`status` を `done` に変える。マージは所有者の申告か `gh pr view <番号> --json state` で確かめる。PR の状態を読むことは、扱わないことに挙げた GitHub Issues の操作には当たらない。issue は消さず、位置も動かさない。

完了条件: 書き換えたあとスクリプトが終了コード0で終わり、対象の issue が `done` になっている。

### 6. 報告する

書き換えた issue の id と変わった状態、スクリプトの結果を1行で伝える。`proposed` を追加したときは、承認を待つことを添える。手順2で範囲外と決めたときは、このスキルでは扱わないことと、下の表の行き先を伝える。

完了条件: 書き換えた issue の id と状態、または範囲外と判断した理由を伝えている。

## このスキルで扱わないこと

| 扱わないこと | 行き先 |
|---|---|
| 承認の判断 | 所有者が決める |
| issue に書いた作業の実装 | 通常の作業として進める |
| 作業の分割と依存関係の管理 | 組み方は設計書に書く（`create-design-doc`）。着手の順序は実装時に決める |
| 改善案を探す調査 | 通常の作業として調べ、見つけた案を手順3で記録する |
| ADR と PRD の更新 | `create-adr`、`create-prd` |
| 一覧ページ（`/issues`）の表示と検査の規則の変更 | docs-hub の通常の作業として直す |
| コミット、push、PR | `create-pr` |
| GitHub Issues の操作 | 扱わない |
