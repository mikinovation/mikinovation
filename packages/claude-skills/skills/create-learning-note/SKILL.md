# create-learning-note: 学習ノート作成スキル

学んだ対象を手元の一次資料で調べ、具体例に当てはめて確かめ、`apps/docs-hub/src/content/learn/` の学習ノートとして残す。学習ノートは、プロダクトで採用したかどうかと関係なく、技術の仕組みや考え方を理解した記録である。

`scripts/` のスクリプトは、Base directory（起動時に示される、このスキルのディレクトリ）を前に付けた絶対パスで呼ぶ。カレントディレクトリは mikinovation リポジトリのままにする。

## 手順

### 1. 対象を1つに絞る

学習ノートは1本で1つの対象を扱う。対象は、技術の仕組み（ライブラリやツールの動き）でも、考え方（設計原則、概念、仕様の読み解き）でもよい。ユーザーの依頼に複数の対象が混ざっている場合は、どれを書くかを選ばせる。

対象を決めたら、当てはめる先の候補を1件以上挙げる。当てはめる先は、実行できるコマンド（ビルド、テスト、CLI）、読める実物（依存パッケージの同梱ドキュメントやソース）、リポジトリ内の具体的な箇所、ユーザーの過去の作業のいずれかである。候補が1件も挙がらない対象は、読んだものの要約にしかならないため扱わない。`research` を案内して終わる。候補を絞り込んで確かめたい点ごとに割り当てる作業は、資料を読んだあとの手順3で行う。

`apps/docs-hub/src/content/learn/` にある既存ノートから、`meta` のタイトルと導入文を読み、同じ対象を扱っているか確かめる。同じ対象とは、ライブラリ、ツール、考え方の名前が同じものである。名前が違えば別の対象として新規に作る（`0001` は Next.js の静的書き出しなので、TanStack Start の書き出しは別の対象になる）。同じ対象なら新規に作らず、既存の TSX を更新する作業として進める。手順6で `更新日` を書き換え、学び終えた場合は `状態` を「学習中」から「一巡した」に進める。

完了条件: 対象が1つに絞られ、当てはめる先の候補が1件以上挙がっている。既存ノートの有無を確かめ、新規か更新かが決まっている。

### 2. 一次資料で対象を調べる

次の順で読む。手元の実物を優先し、Web と context7 は、実物からは読めない点の裏取りにだけ使う。

- 依存パッケージの同梱ドキュメントとソース。直接依存は `apps/<アプリ>/node_modules/<パッケージ>` にあり、推移的な依存は一覧に現れないため `apps/<アプリ>/node_modules/.pnpm/` を探す。どのパッケージに実装があるか分からない場合は、`.pnpm` のディレクトリ名を一覧して当たりを付け、そのパッケージの中を grep する。実体の版は `package.json` の指定と食い違うことがあるため、出典には実体の `package.json` の版を書き、パスは `.pnpm` の実体パスではなくパッケージ名からの相対パスで書く
- リポジトリ内の、その仕組みや考え方が現れている箇所のコードと設定
- 対象が Agent Skill や Claude Code の設定なら、正本は `packages/claude-skills/skills/<スキル名>/` にある。配置後の SKILL.md と同梱ファイルは `~/.claude/skills/<スキル名>/` にある。Nix の設定は `packages/dotfiles/nix/programs/claude-code/` にある
- 公式ドキュメント、提唱者の文章（WebFetch、context7）

規約と見本として、`apps/docs-hub/FIGURES.md` の学習ノートの決まりと、`apps/docs-hub/src/content/learn/` の既存ノートを読む。`apps/docs-hub/README.md` の「文書」の節で保存先と索引の決まりを確かめる。`src/content/` の prd、adr、design は、本文から参照先として引くときだけ読む。

完了条件: 要点に書く主張のすべてに一次資料の裏付けがあり、その一覧が出典の節にまとまっている。出典に書くのは、ファイルのパス、実行したコマンドと日付、または URL である。

### 3. 当てはめて確かめる

確かめたことを2つ以上立て、その一つ一つに、手順1で挙げた候補から当てはめる先を割り当てる。立てた一つ一つが、下の表の「確かめたこと」の1行になる。確かめたこと1つに複数の箇所を当ててよい。実行できるコマンドなら実行して出力を見る。考え方なら、リポジトリの該当箇所か過去の作業に当て、当てはまる箇所と当てはまらない箇所を挙げる。

確かめた結果は「確かめたこと」「方法」「結果」の3列で記録する。結果には、数えた件数、出力のパス、当てはめた対象のファイルと行のように、実物から引ける事実だけを書く。各セルは下書きの Markdown で60文字以内に収め、収まらない件数やパスは表の下の段落に書く。tanteki の検査が表のセルの長さで落ちるためである。

確かめた結果が調べた説明と食い違った場合は、説明ではなく実物を採り、食い違いを要点に書く。

完了条件: 3列の行が2行以上あり、各行の結果を実物から引ける。

### 4. grilling で残りの項目を詰める

`Skill` ツールで `grilling` を呼び、次の4項目を論点として詰める。手順2と手順3で埋まった事実は聞かず、埋まったことをユーザーに伝える。

| # | 項目 | 何のために聞くか |
|---|---|---|
| 1 | 学ぶ動機 | どの作業に合わせて調べたかを示す |
| 2 | 扱わない範囲 | 1本で扱う対象の境目を決める |
| 3 | 状態 | 学習中か一巡したかを決める |
| 4 | 更新日 | 見直しの期限の基準日を決める |

4項目はユーザーが決めることであり、調べて埋める事実ではない。推奨回答は提案であると明示し、ユーザーが承認するまで材料に書き込まない。4項目は互いに独立しているため、1ラウンドでまとめて聞く。事実は手順2と手順3で埋め終えているため、grilling が求める調査のサブエージェントは起動しない。

読者は開発者で固定する。この項目は質問にせず、手順5の材料一覧に書いて示す。

ユーザーが決まっていないと答えた項目は `TBD` として次へ進む。ただし学ぶ動機が `TBD` のままでは手順5へ進まない。動機のないノートでは、何を学んだかを読者が判断できないためである。

完了条件: 4項目に回答か `TBD` が入っている。

### 5. 材料一覧を提示して合意を取る

手順2と手順3の結果から、学んだ仕組みや考え方の要点を自分の言葉でまとめる。読んだ説明の引き写しではなく、何がどう動くのか、何に当てはまるのかを述べる。

一覧には読者（開発者）、学ぶ動機、扱わない範囲を示す。続けて要点、確かめた結果の3列、出典を並べ、状態と更新日を添える。`TBD` の件数も併記する。あわせて、図にする対象を1件挙げる。仕組みの構成要素とその間を流れるデータ、入力から出力に至る変換の段階、考え方の分類や対比、判断の分かれ目のいずれかを1枚で示すものとする。表や文章で足りるものは挙げない。図は下書きに入れず、手順6で TSX へ移すときに自分で描く。

完了条件: ユーザーが材料と図の対象を承認している。

### 6. japanese-review に執筆を渡す

`Skill` ツールで `japanese-review` を呼び、次を渡して学習ノートを執筆させる。

| 項目 | 渡すもの |
|---|---|
| 依頼 | `執筆`（既存ノートの更新も `執筆`） |
| 対象 | 下書きの Markdown の絶対パスと、下に書いた保存先とファイル名の規則 |
| 文書の種類 | 学習ノート。textlint の `--type` は `stock` |
| 立場 | `説明` |
| 変えないこと | 節の並び、確かめた結果の表の3列、出典に挙げた項目 |
| 原資料 | 手順5で合意した材料 |

japanese-review が扱うのは下書きの Markdown だけである。TSX への移し替えと図は、下書きが仕上がってから自分で行う。

保存先は `apps/docs-hub/src/content/learn/` に固定する。保存先はユーザーに聞かず、japanese-review にも渡す。ファイル名は `<番号>_<タイトル>.tsx` とし、番号は、保存先にある既存ノートの最大番号に1を足し、4桁のゼロ埋めにする。タイトルは学んだ対象を表す英小文字の語で、複数語はハイフンでつなぐ。例: `0002_tanstack-start-prerender.tsx`

```sh
ls apps/docs-hub/src/content/learn | sed -n 's/^\([0-9]\{4\}\)_.*/\1/p' | sort | tail -n 1
```

ノートが属するリポジトリを決め、`meta` の `repository` に書く。使える ID は `apps/docs-hub/src/lib/repositories.ts` の `repositoryIds` にある値だけで、確かめた結果を取った場所、または当てはめた具体例があるリポジトリから決める。判断できないときだけユーザーに聞く。

属性、節の `label`、図の決まりについては、`apps/docs-hub/FIGURES.md` の学習ノートの項が正本である。この規約に従って書くことを japanese-review に渡す。独自の用語を使う場合だけ、本文の冒頭に `Terms` を置く。

節の `title` は次のとおりである。

| `label` | `title` |
|---|---|
| Motivation | 学ぶ動機 |
| Summary | 要点（仕組みを扱うなら仕組みの要点） |
| Verification | 確かめたこと（コマンドを実行したなら手元で動かした結果） |
| Sources | 出典 |

`meta.lead` には、何を扱い、何を確かめたノートかを2文以内で書く。下書きの冒頭の段落をこれに充てる。下書きでは属性を本文に混ぜず、冒頭に `属性: 読者は開発者、状態は…、更新日は…` の1行として置く。TSX へ移すときに `meta.attributes` へ移す。図は Summary の節に1枚入れ、HTML と SVG で書く。Mermaid は使わない。確かめた結果は「確かめたこと」「方法」「結果」の3列の `DocTable` にする。

出典は、参照先があるものをリンクで書く。同梱のドキュメントとリポジトリ内のファイルはパスを文字のまま挙げ、実行した結果は実行日を添える。外部の資料は URL を指す。本文中の文書参照は `<DocRef kind="ADR" number="0017" />` と書き、手でリンクにしない。

下書きは一時ディレクトリ（例: `$(mktemp -d)`）に、保存先と同じ名前の `<番号>_<タイトル>.md` として置き、リポジトリに残さない。下書きも `apps/docs-hub/FIGURES.md` の決まりに従い、列挙を箇条書きにせず表か地の文で書く。図は下書きに入れず、図にする対象を Summary の節の末尾に `図にする対象: …` として書く。1文が100文字を超えると検査で落ちるため、短い2文に分けてよい。出典もパッケージ名やスキル名からの相対パスで書いて1文を短く保つ。

japanese-review が下書きを仕上げたら、本文を `apps/docs-hub/FIGURES.md` のコンポーネントに移し替え、図を描く。保存先は `apps/docs-hub/src/content/learn/<番号>_<タイトル>.tsx` である。このとき日本語の段落は改行せず1行で書く。JSX は本文中の改行を半角空白にするため、自分で折り返すと表示時に文の途中へ空白が入る。整形は英数字と日本語の境目のように元から半角空白がある位置でだけ行を折るため、整形が入れた折り返しは表示を変えない。整形後に出た折り返しはそのまま残す。

保存したら次を実行する。

```sh
<Base directory>/scripts/finalize.sh apps/docs-hub/src/content/learn/<番号>_<タイトル>.tsx
```

既存のノートを更新する場合は、正本の TSX を直し、`更新日` を書き換える。日本語を書き換えるときは、その範囲だけを一時ファイルの Markdown に写して japanese-review に通し、TSX へ戻す。

完了条件: `finalize.sh` が終了コード0で終わる。

## このスキルで扱わないこと

- 採否の決定の記録（`create-adr` の領分）
- 問いに答えるための調査メモ（`research` の領分）
- 節構成、見出し、本文の表現、textlint による検査と合格判定（`japanese-review` の領分）
- 既存ノートの推敲だけの依頼
- コミット、push、PR（必要なら `create-pr` を使う）
- `apps/docs-hub/FIGURES.md` の学習ノートの項以外の規約と、本文のコンポーネントそのものの改訂
