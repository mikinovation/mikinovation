# create-plan: 実装計画作成スキル

設計書一つに対して、実装の計画を一つ作る。このスキルは、作業をスライスに分けて合意を得てから japanese-review に執筆を渡す。コードは書かない。

計画と進捗は、`docs/plan/` の Markdown だけで管理する。GitHub の Issue など、外部の課題管理にチケットを作らない。

文書の役割を次のように分ける。計画は前提の文書に沿って作業を分けるだけで、それらの内容を決め直さない。

| 文書 | 答える問い | 作るスキル |
|---|---|---|
| PRD | 何を、なぜ作るか | create-prd |
| ADR | どの方式を選ぶか | create-adr |
| 設計書 | 選んだ方式で、どう組むか | create-design-doc |
| テストケース一覧 | どの振る舞いを、どの入力と期待値で確かめるか | create-test-cases |
| 計画 | どの順に、どの単位で作り、何をもって終わりとするか | このスキル |

計画は、実装者が一人では決められないことだけを書く。設計書とテストケース一覧で決まっていることを繰り返さず、参照する。

## スライスの規則

計画は、次の規則でスライスに分ける。

- 縦に切る: 一つのスライスは、データ、処理、入出力、テストのすべての層を細く貫く。一つの層だけを作るスライスにしない。
- 単独で確かめられる: スライスを終えると、そのスライスに割り当てたテストケースが通る。
- 一つのコンテキストに収まる: 新しいセッションの実装者が、計画、設計書、テストケース一覧を読んだうえで、一度に終えられる大きさにする。
- 下準備を先に置く: 既存のコードを変えやすくする整理（下準備）が要る場合は、独立したスライスにして先頭に置く。
- 広い変更は段階に分ける: 一つの機械的な変更が多数の呼び出し元に及ぶ場合は縦に切らず、新しい形を足す、呼び出し元を移す、古い形を消す、の順のスライスに分ける。
- 依存は本当に必要なものだけ: あるスライスが別のスライスを待つのは、その成果を使う場合だけにする。依存のないスライスは並行して進められる。

完了条件は、テストケースの ID で表す。テストケース一覧のケースは、どれか一つのスライスにだけ割り当てる。

## 手順

### 1. 対象を定める

ユーザーの依頼から、前提とする設計書と、既存の計画があるかを確認する。

設計書と同じ番号のテストケース一覧が `docs/test/` にない場合は、create-test-cases で先に作ることを推奨回答として示す。完了条件をテストケースの ID で表せないためである。

### 2. 前提の文書とコードを読む

リポジトリルートの次の文書を読む。

- `docs/design/` の設計書
- `docs/test/` のテストケース一覧
- `docs/prd/` の、設計書が前提とする PRD
- `docs/adr/` の、設計書の「前提とする決定」に挙げた ADR
- `docs/plan/` の既存の計画

既存のコードを読み、設計書の構成のうち、どこまでがすでにあるかを把握する。下準備の候補もここで探す。調べた事実は、手順5の推奨回答の根拠として示す。

読んだ文書の一覧を示し、過不足がないかを確かめる。これは前提の確認であり、執筆の承認ではない。

### 3. 計画できない作業を洗い出す

次のいずれかに当たる作業は、計画に入れずに止める。

| 状況 | 案内するスキル |
|---|---|
| スライスが前提にするコンポーネントの層3が設計書にない | create-design-doc |
| 方式が ADR で決まっていない論点がある | create-adr |
| テストケース一覧の未解決点に、期待値が決まっていない観点がある | create-test-cases |
| 設計書の構成のうち、どのテストケースにも対応しない部分がある | create-test-cases |

該当する作業の一覧を示し、先に前提の文書を整えることを推奨回答として示す。ユーザーが先に進めると答えた作業は、計画の「保留した作業」に入れ、スライスにしない。

### 4. 読者を確認する

計画の読者は、実装する開発者と、実装を任されるエージェントである。エージェントは計画と前提の文書だけを手がかりに作業を始める。これを提示し、異なる読者を想定している場合だけ修正を求める。質問としては投げない。

### 5. grilling でスライスを決める

「スライスの規則」に従ってスライスの案を作り、番号付きの一覧で示す。各スライスには次を添える。

- 見出し: 何ができるようになるかを短く表す
- 作るもの: 利用者や呼び出し元から見て、何ができるようになるか
- 依存: 先に終える必要があるスライスの番号。ない場合は「なし」
- 対象: 設計書の層2のどのコンポーネントにまたがるか
- 完了条件: 割り当てたテストケースの ID
- 手で確かめること: 自動テストで確かめられず、テストケース一覧で意図して扱わない振る舞いとしたもののうち、このスライスで確かめるもの

`Skill` ツールで `grilling` を呼び、次を詰める。

- 粒度: 粗すぎるスライス、細かすぎるスライスはないか
- 依存: 本当に必要な依存だけか。並行できるのに直列にしていないか
- 結合と分割: まとめるべきスライス、分けるべきスライスはないか

計画の中で、設計書やテストケース一覧にない決定をしない。スライスを切るために新しい決定が要る場合は、手順3に戻り、該当する作成スキルを案内する。

### 6. 計画を検査する

`Agent` ツールで、聞き取りの経緯を知らない独立したサブエージェントを起こす。サブエージェントには、前提の文書のパスと、スライスの一覧だけを渡し、次を検査させる。

- テストケース一覧のケースのうち、どのスライスにも割り当てていないもの、または二つ以上に割り当てたもの
- 完了条件のケースが一つもないスライス（下準備のスライスを除く）
- 依存の循環
- 依存先のスライスより前に、その成果を使うスライス
- 一つの層だけを作る、横に切ったスライス
- 計画の中で新しく決定している内容

サブエージェントには、結果を `合格`、`要修正`、`設計へ戻す` のいずれかと、指摘の一覧で返させる。

- `要修正`: 指摘を反映し、もう一度検査する。修正と検査は2回までとする。2回で合格しなければ、残った指摘をユーザーに示す。
- `設計へ戻す`: 前提の文書が足りず、スライスを切れない場合である。不足している記述を示し、手順3の表の作成スキルを推奨回答として示す。

### 7. 材料一覧を提示して合意を取る

次を示し、この内容で計画を書いてよいか確認し、承認を待つ。執筆の承認はここで一度だけ得る。

- 前提の文書
- スライスの一覧と依存
- テストケースの割り当て（ケースの総数と、割り当てた数）
- 保留した作業
- 計画の検査の結果

### 8. japanese-review に執筆を渡す

`Skill` ツールで `japanese-review` を呼び、依頼を執筆、立場を `決まり` として、確定した材料を渡して計画を執筆させる。文書の種類は作業を進めるための計画とし、検査の種類には `flow` を指定させる。計画は進捗の記録を含むため、チェックボックスを使ってよい。

次の構成を japanese-review に渡す。

- 冒頭: 前提の PRD、設計書、テストケース一覧を書く。続けて「進捗の記録」の規則を書く。
- 全体の順序: スライスの依存を Mermaid の図で示す。最初に着手できるスライスを示す。
- スライスごとの節: 「スライスの節の形式」のとおりに書く。
- 保留した作業: 作業と、保留した理由、整えるべき前提の文書を書く。
- 出典: 前提の文書を書く。

最後のスライスとして、CI の照合の対象にこの設計書の番号を加える作業を置く。依存は、ほかのすべてのスライスとする。完了条件は、CI で `check-test-ids --only <設計書の番号>` が合格することとする。

リポジトリのファイルパスとコードの断片は本文に含めない。陳腐化しやすいためである。

計画の保存先は、リポジトリルートの `docs/plan/` に固定する。ファイル名は、前提の設計書と同じ `<番号>_<タイトル>.md` とする。保存先をユーザーに問わず、japanese-review にも渡す。

既存の計画を更新する場合は、同じファイルを更新させる。着手済みのスライスの番号を変えさせず、完了したスライスの記述を変えさせない。

#### スライスの節の形式

進捗を Markdown の上で追えるように、次の形式を崩さない。

```markdown
### スライス 03: 日割り月の基本額を計算できる

- 状態: 未着手
- 作るもの: 日割り月の稼働率を指定すると、基本額と精算幅がその比率で計算される
- 依存: スライス 01、スライス 02
- 対象: 読み込み、集計

完了条件:

- [ ] TC-0001-021
- [ ] TC-0001-022

手で確かめること:

- [ ] 勤怠表 PDF の基本額の欄に、日割りの額が載る
```

| 項目 | 内容 |
|---|---|
| 状態 | `未着手`、`着手`、`完了` のいずれか |
| 依存 | 先に完了している必要があるスライス。ない場合は「なし」 |
| 完了条件 | 割り当てたテストケースの ID。テストが通ったらチェックを入れる |
| 手で確かめること | ない場合は項目ごと省く |

#### 進捗の記録

計画の冒頭に、次の規則を書かせる。実装する人とエージェントは、この規則で計画を更新する。

- 着手できるスライスは、状態が `未着手` で、依存するスライスがすべて `完了` のものである。複数あれば番号の小さいものから着手する。
- 着手するときに、状態を `着手` にする。
- 完了条件のテストが通るたびに、そのケースにチェックを入れる。
- 完了条件と手で確かめることのすべてにチェックが入ったら、状態を `完了` にする。
- 計画を更新する変更は、そのスライスの実装と同じコミットに含める。

### 9. 実装に引き渡す

次を案内して終える。

- スライスを一つずつ実装する: 着手できるスライスを一つ選び、`Skill` ツールで `tdd` を呼び、完了条件のケースから実装する。テスト名にはケース ID を入れる。
- 進捗を確かめる: 計画の各スライスの状態と、`check-test-ids --only <設計書の番号>` の結果を見る。CI に入れる前でも、手元で実行すれば、テストのないケースが分かる。

## このスキルで扱わないこと

- 要求、方式、設計、テストケースの決定（それぞれ PRD、ADR、設計書、テストケース一覧の領分）
- コードの実装（tdd の領分）
- 担当と期限の管理
- GitHub の Issue など、外部の課題管理へのチケットの作成
- 工数の見積もり
