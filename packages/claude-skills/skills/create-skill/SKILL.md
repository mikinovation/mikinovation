# create-skill: スキル作成スキル

スキルの材料を grilling で聞き取り、writing-for-agents に沿って書き、試しに実行して直してから、ユーザーの承認を得る。コミットと PR は行わない。

このスキルが呼ぶスキルをプラグインとして導入した環境では、`mattpocock-skills:grilling` のように名前空間の付いた名前で呼ぶ。

`scripts/` のスクリプトは、Base directory（起動時に示される、このスキルのディレクトリ）を前に付けた絶対パスで呼ぶ。例えば `<Base directory>/scripts/check.sh` である。スクリプトはカレントディレクトリからリポジトリを探す。そのため、カレントディレクトリは作業するリポジトリのままにする。

## 手順

### 1. 既存スキルを調べる

次の場所にある各スキルの `SKILL.md` の frontmatter（name と description）だけを読む。ほかの場所は探索しない。

- 実行中のリポジトリの `.claude/skills/`。mikinovation リポジトリ（`packages/claude-skills/skills/` がある）では `packages/claude-skills/skills/` だけを読む。`.claude/skills/` はそこへのリンクである
- 起動中のセッションに一覧として示されているスキル。一覧の description をすべて読む。同じ名前のスキルがリポジトリにもある場合は、リポジトリのファイルの description を採る

description から役割の重なりの候補が見つからなくても、作るスキルの中心となる操作の語（例: TODO の収集なら `TODO`）で、リポジトリのスキルの本文を `grep` する。当たったスキルは本文を読み、重なりかどうかを確かめる。

完了条件: 作ろうとしているスキルと名前が重なるもの、役割が重なるものを、それぞれ列挙できている（なければ「なし」）。この結果は手順2の推奨回答に使う。

### 2. grilling で11項目を詰める

先に `Skill` ツールで `writing-for-agents` を呼び、同じディレクトリの `SKILL-MECHANICS.md` も読む。推奨回答と手順4の執筆は、この2つの指針に従う。

次に `Skill` ツールで `grilling` を呼び、次の11項目を論点として詰める。目的を設計の木の根とし、目的が合意されるまでほかの項目を聞かない。項目2以降も、前提となる項目が決まるまでは、それに依存する項目を後のラウンドに回す。

| # | 項目 | 何を決めるか |
|---|---|---|
| 1 | 目的 | そのスキルで何ができるようになり、どんな作業をなくすか |
| 2 | name | ディレクトリ名と同じ英小文字とハイフンの名前。手順1の重なりを避ける |
| 3 | 起動の仕方 | model-invoked か user-invoked か |
| 4 | description | 何をするスキルか、起動する場面（「…」などで使用）、使わない場面（…には使わない）。起動の仕方によらず両方の場面を書く |
| 5 | 隣のスキルとの分担 | 手順1で見つけた重なりを、どちらが何を受け持つかで分ける |
| 6 | どこを見るか | 読む資料とその場所、読まない場所、対象の判定基準 |
| 7 | どう進めるか | 手順の並びと、各手順の完了条件 |
| 8 | どう書くか | 成果物の形式、ひな形、保存先、ファイル名の規則。該当なし、重複、例外のときの出力 |
| 9 | スクリプトにする手順 | 7のうち、判断を要さず決まった処理で済む手順。`scripts/` に出す |
| 10 | 呼び出すスキル | 中で使う他のスキルと、渡すもの |
| 11 | 扱わないこと | ほかのスキルや文書に任せる範囲 |

model-invoked は、エージェントや他のスキルが呼べるスキルである。user-invoked は、`disable-model-invocation: true` を付け、人が名前を打ったときだけ動くスキルである。起動の仕方は `SKILL-MECHANICS.md` に従って推奨する。エージェントや他のスキルが自分で呼ぶ必要がなければ user-invoked を推奨する。

`SKILL-MECHANICS.md` は user-invoked の description を1行の要約にする。このスキルでは、user-invoked でも起動する場面と使わない場面の両方を description に書く。人がスキルの一覧から選ぶときにも、どれを使うかを description だけで判断できるようにするためである。`check.sh` もこの決まりで検査する。

スクリプトにする手順は、7の各手順について「同じ入力で毎回同じ結果になるか」を確かめて推奨する。ファイルの配置、登録、形式の検査、決まった変換はスクリプトにする。

項目6の判定基準では、対象に含めるものと除くものを決め、曖昧な語（「コメント」「生成物」など）は具体例で定める。判定基準を決めたら、リポジトリの実際のファイルで当てはまりそうな行を `git grep` などで探し、基準に当てはめる。誤って含まれる行と誤って除かれる行の実例をユーザーに示し、基準を確かめる。

ユーザーが決まっていないと答えた項目は `TBD` として次へ進む。ただし、1、2、4、7のいずれかが `TBD` のままでは手順3へ進まない。

完了条件: 11項目すべてに回答か `TBD` が入っている。

### 3. 材料一覧を提示して合意を取る

11項目を一覧で示し、`TBD` の件数を併記する。あわせて、試しの実行（手順6）で使う例題を提案する。例題は、そのスキルを使う実際の作業1〜2件と、description の判定に使う「使わない場面」の依頼文1件とする。作業の例題には、期待する結果（成果物に含まれるべきもの、含まれるべきでないもの）を添える。

完了条件: ユーザーが材料と例題を承認している。

### 4. SKILL.md と scripts を書く

`Skill` ツールで `writing-for-agents` を呼び、その指針と `SKILL-MECHANICS.md` に沿って書く。既存スキルの書き方（見出しの「手順」「このスキルで扱わないこと」、各手順の完了条件）にそろえ、日本語で書く。

保存先は実行中のリポジトリで決まる。

- mikinovation リポジトリ（`packages/claude-skills/skills/` がある）: `packages/claude-skills/skills/<name>/`
- それ以外: `.claude/skills/<name>/`

すべての分岐で使う内容は SKILL.md に書き、一部の分岐でしか使わない参照は同じディレクトリの別ファイルに分けてリンクする。分けた場合は理由をユーザーに伝える。項目9の手順は `scripts/` にスクリプトとして書き、SKILL.md にはスクリプトの呼び出しと、終了コードで判定する完了条件だけを書く。終了コードは、0を成功（該当なしを含む）、1を処理の失敗（検査のスクリプトでは検査の不合格）、2を使い方や実行場所の誤りとし、`check.sh` と同じ規約にそろえる。

完了条件: 項目1〜11のすべてが、SKILL.md か scripts のどこかに反映されている。SKILL.md が述べる判定の決まりを scripts が実際に満たしていることを、判定の決まりごとに当てはまる行と外れる行の実例で確かめている。

### 5. 登録して機械的に検査する

mikinovation リポジトリでは、次を実行して `.claude/skills/` のシンボリックリンクと Nix の skills 一覧に登録する。

```sh
<Base directory>/scripts/register.sh <name>
```

どのリポジトリでも、次を実行する。

```sh
<Base directory>/scripts/check.sh <作ったスキルのディレクトリ>
```

`NG:` が出たら、示された箇所を直して再実行する。

完了条件: `check.sh` が終了コード0で終わる。

### 6. 試しに実行して直す

`Agent` ツールで、この会話の文脈を持たないサブエージェントを起動し、次を渡す。

- 作ったスキルの SKILL.md のパス（scripts も読めるようにディレクトリのパスも渡す）
- 手順3で合意した例題と、ユーザーへの質問に対する想定回答
- 成果物は scratchpad などリポジトリ外の一時ディレクトリに書くこと。リポジトリへの変更、コミット、外部への投稿はしないこと
- 手順3で合意した期待する結果
- 報告の形式: 実行した手順ごとに、迷った箇所、飛ばした手順、推測で補った事実、期待する結果と食い違った出力、スクリプトの終了コード

別に、description の判定を試す。手順1の既存スキルの description 一覧に、作ったスキルの description を加えてサブエージェントに渡す。例題の依頼文と「使わない場面」の依頼文のそれぞれについて、どのスキルを起動するかを答えさせる。

迷った箇所、推測で補った事実、期待する結果との食い違い、description の判定の誤りを失敗とみなす。報告を読んで失敗ごとの原因の手順を特定し、次のいずれかで直す。

- 指示が曖昧、推測で補わせた: 見る場所、判定基準、書き方、進め方を具体的に書く。ユーザーが決める事実なら、手順2に戻って聞く
- 終わりが曖昧: 完了条件を確かめられる形にする
- 決まった処理を手で行っていた: スクリプトにする
- 起動の判定を誤った: description の起動する場面か使わない場面を直す

直したら手順5の `check.sh` を再実行し、新しいサブエージェントで再び試す。試行は最大3回とし、手順2に戻って聞き直した場合も回数は通算で数える。

`Agent` ツールが使えない環境では、自分で SKILL.md だけを頼りに例題を実行し、手順書に書かれていないことを補った箇所をすべて「推測で補った」として記録する。手順8では、その試行が文脈を持つ者による試しであることを伝える。

完了条件: 最後の試行で失敗が報告されない。3回で失敗が残った場合は、残った失敗と原因をユーザーに報告する。

### 7. japanese-review で日本語を整える

`Skill` ツールで `japanese-review` を呼び、SKILL.md と分けた参照ファイルを1ファイルずつ推敲させる。次を渡す。

| 項目 | 渡すもの |
|---|---|
| 依頼 | `推敲` |
| 対象 | ファイルの絶対パス |
| 文書の種類 | エージェントが読む手順書（スキル）。textlint の `--type` は `stock` |
| 立場 | `決まり` |
| 変えないこと | 次の段落に挙げるもの |
| 原資料 | 手順3で合意した材料一覧 |

変えないことには、frontmatter、見出し、表の構造、コードブロック、コマンド、パス、スキル名、各手順の完了条件が求める条件そのもの、繰り返して使う決まった語（leading word）を渡す。完了条件の文は、条件を変えない言い換えなら直してよいと伝える。

japanese-review の結果と差分を `writing-for-agents` の指針に照らし、指針とぶつかる変更は元に戻す。例えば、決まった語を言い換えた変更、完了条件をぼかした変更、肯定形の指示を禁止形にした変更、別ファイルに分けた参照を本文に戻した変更である。textlint の指摘のうち指針とぶつかるものは採らず、採らなかった指摘と理由を手順8で示す。意味や条件を変える修正も採らない。

整えたあと手順5の `check.sh` を再実行する。

完了条件: `check.sh` が終了コード0で終わり、textlint の指摘がすべて、直したか、採らなかった理由を書いたかのどちらかになっている。

### 8. 下書きを提示して承認を取る

作ったファイルの一覧、SKILL.md の全文、試しの実行の結果（試行回数と、直した手順）、japanese-review の結果と採らなかった textlint の指摘を示し、承認を待つ。修正を求められたら手順4に戻る。

完了条件: ユーザーが承認している。

## このスキルで扱わないこと

- 既存スキルの改修と推敲
- コミット、push、PR（必要なら `create-pr` を使う）
- `skill-creator` による評価とベンチマーク
