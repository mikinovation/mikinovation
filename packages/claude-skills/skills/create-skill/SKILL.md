# create-skill: スキル作成スキル

スキルの材料を grilling で聞き取り、writing-for-agents に沿って書き、試しに実行して直してから、ユーザーの承認を得る。コミットと PR は行わない。

このスキルが呼ぶスキルをプラグインとして導入した環境では、`mattpocock-skills:grilling` のように名前空間の付いた名前で呼ぶ。`scripts/` は、このスキルのディレクトリ（起動時に示される Base directory）からの相対パスで呼ぶ。

## 手順

### 1. 既存スキルを調べる

次の場所にある各スキルの `SKILL.md` の frontmatter（name と description）だけを読む。ほかの場所は探索しない。

- 実行中のリポジトリの `.claude/skills/`
- mikinovation リポジトリなら `packages/claude-skills/skills/`
- 起動中のセッションに一覧として示されているスキル

完了条件: 作ろうとしているスキルと名前が重なるもの、役割が重なるものを、それぞれ列挙できている（なければ「なし」）。この結果は手順2の推奨回答に使う。

### 2. grilling で11項目を詰める

`Skill` ツールで `grilling` を呼び、次の11項目を論点として詰める。目的を設計の木の根とし、目的が合意されるまでほかの項目を聞かない。2以降も、前提となる項目が決まるまで、それに依存する項目は後のラウンドに回す。

| # | 項目 | 何を決めるか |
|---|---|---|
| 1 | 目的 | そのスキルで何ができるようになり、どんな作業をなくすか |
| 2 | name | ディレクトリ名と同じ英小文字とハイフンの名前。手順1の重なりを避ける |
| 3 | 起動の仕方 | model-invoked（エージェントや他のスキルが呼べる）か、user-invoked（`disable-model-invocation: true`、人が名前を打ったときだけ動く）か |
| 4 | description | 何をするスキルか、起動する場面（「…」などで使用）、使わない場面（…には使わない）。起動の仕方によらず両方の場面を書く |
| 5 | 隣のスキルとの分担 | 手順1で見つけた重なりを、どちらが何を受け持つかで分ける |
| 6 | どこを見るか | 入力として読む資料と、その場所。読まない場所も決める |
| 7 | どう進めるか | 手順の並びと、各手順の完了条件 |
| 8 | どう書くか | 成果物の形式、ひな形、保存先、ファイル名の規則 |
| 9 | スクリプトにする手順 | 7のうち、判断を要さず決まった処理で済む手順。`scripts/` に出す |
| 10 | 呼び出すスキル | 中で使う他のスキルと、渡すもの |
| 11 | 扱わないこと | ほかのスキルや文書に任せる範囲 |

起動の仕方は、`writing-for-agents` の `SKILL-MECHANICS.md` に従って推奨する。エージェントや他のスキルが自分で呼ぶ必要がなければ user-invoked を推奨する。

スクリプトにする手順は、7の各手順について「同じ入力で毎回同じ結果になるか」を確かめて推奨する。ファイルの配置、登録、形式の検査、決まった変換はスクリプトにする。

ユーザーが決まっていないと答えた項目は `TBD` として次へ進む。ただし、1、2、4、7のいずれかが `TBD` のままでは手順3へ進まない。

完了条件: 11項目すべてに回答か `TBD` が入っている。

### 3. 材料一覧を提示して合意を取る

11項目を一覧で示し、`TBD` の件数を併記する。あわせて、試しの実行（手順6）で使う例題を提案する。例題は、そのスキルを使う実際の作業1〜2件と、description の判定に使う「使わない場面」の依頼文1件とする。

完了条件: ユーザーが材料と例題を承認している。

### 4. SKILL.md と scripts を書く

`Skill` ツールで `writing-for-agents` を呼び、その指針と `SKILL-MECHANICS.md` に沿って書く。既存スキルの書き方（見出しの「手順」「このスキルで扱わないこと」、各手順の完了条件）にそろえ、日本語で書く。

保存先は実行中のリポジトリで決まる。

- mikinovation リポジトリ（`packages/claude-skills/skills/` がある）: `packages/claude-skills/skills/<name>/`
- それ以外: `.claude/skills/<name>/`

すべての分岐で使う内容は SKILL.md に書き、一部の分岐でしか使わない参照は同じディレクトリの別ファイルに分けてリンクする。分けた場合は理由をユーザーに伝える。項目9の手順は `scripts/` にスクリプトとして書き、SKILL.md からはスクリプトの呼び出しと、終了コードで判定する完了条件だけを書く。

完了条件: 項目1〜11のすべてが、SKILL.md か scripts のどこかに反映されている。

### 5. 登録して機械的に検査する

mikinovation リポジトリでは、次を実行して `.claude/skills/` のシンボリックリンクと Nix の skills 一覧に登録する。

```sh
scripts/register.sh <name>
```

どのリポジトリでも、次を実行する。

```sh
scripts/check.sh <作ったスキルのディレクトリ>
```

`NG:` が出たら、示された箇所を直して再実行する。

完了条件: `check.sh` が終了コード0で終わる。

### 6. 試しに実行して直す

`Agent` ツールで、この会話の文脈を持たないサブエージェントを起動し、次を渡す。

- 作ったスキルの SKILL.md のパス（scripts も読めるようにディレクトリのパスも渡す）
- 手順3で合意した例題と、ユーザーへの質問に対する想定回答
- 成果物は scratchpad などリポジトリ外の一時ディレクトリに書くこと。リポジトリへの変更、コミット、外部への投稿はしないこと
- 報告の形式: 実行した手順ごとに、迷った箇所、飛ばした手順、推測で補った事実、誤った出力、スクリプトの終了コード

別に、description の判定を試す。手順1の既存スキルの description 一覧に作ったスキルの description を加えてサブエージェントに渡し、例題の依頼文と「使わない場面」の依頼文のそれぞれについて、どのスキルを起動するかを答えさせる。

報告を読み、失敗ごとに原因になった手順を特定し、次のいずれかで直す。

- 指示があいまい: 見る場所、書き方、進め方を具体的に書く
- 終わりが曖昧: 完了条件を確かめられる形にする
- 決まった処理を手で行っていた: スクリプトにする
- 起動の判定を誤った: description の起動する場面か使わない場面を直す

直したら手順5の `check.sh` を再実行し、新しいサブエージェントで再び試す。試行は最大3回とする。

完了条件: 最後の試行で失敗が報告されない。3回で失敗が残った場合は、残った失敗と原因をユーザーに報告する。

### 7. yomiyasu で日本語を整える

`Skill` ツールで `yomiyasu` を呼び、SKILL.md と分けた参照ファイルの日本語を整える。frontmatter のキー、コマンド、パス、スキル名、コードブロックは変えない。意味や条件を変える修正は採らない。整えたあと手順5の `check.sh` を再実行する。

完了条件: `check.sh` が終了コード0で終わる。

### 8. 下書きを提示して承認を取る

作ったファイルの一覧、SKILL.md の全文、試しの実行の結果（試行回数と、直した手順）を示し、承認を待つ。修正を求められたら手順4に戻る。

完了条件: ユーザーが承認している。

## このスキルで扱わないこと

- 既存スキルの改修と推敲
- コミット、push、PR（必要なら `create-pr` を使う）
- `skill-creator` による評価とベンチマーク
- tanteki と japanese-review による textlint の検査
